## 2. Executive summary

Top-Lab is a substantial and well-structured implementation. At the audited commit it is **not** at functional parity with the canonical reference, but the shortfall is concentrated and mostly of a *reachability* kind rather than a *capability* kind. Of the 306 in-scope canonical functions assessed, **203 are matched** (66.3%), 9 are partial, 8 differ materially, 72 are missing and 14 cannot be resolved from the available evidence.

**Overall implementation status.** The core laboratory workflow — patient registration, test selection, result entry, review, printing, settlement and delivery — is implemented end to end and is backed by a working test suite. The shortfall clusters around three things: (a) action bands and screens that the reference specifies but Top-Lab reaches by a different route or not at all; (b) two data-protection and accounting behaviours that are configured but never enforced or never expressible; and (c) several reference modules (utilities, auditing, sample withdrawal, statistics preview) that are thin or absent.

**The most consequential findings.**

- **The print-result password protects nothing.** Top-Lab stores a hashed password, ships a verifier for it, and unit-tests that verifier — and then never calls it. The verifier's only non-test references in the whole repository are its own declaration and a DI registration. No result print, receipt print, invoice print, envelope print, bulk print or delivery print consults it. The password is also a single global setting, while the reference defines it as a *per-patient* field in the patient screen's Notes and Communication Block, and the reference requires the password to be printed on the receipt — Top-Lab's receipt carries no password at all. *(GAP-01, GAP-02, GAP-03)*
- **The delivery screen has almost no action band.** The reference gives the delivery screen eleven actions. Top-Lab's delivery list and delivery handover together offer load, group slips, back, and the settlement controls. Printing, preview, copy, patient data, combined report, medical history, empty report, envelope print and notes are all unreachable from the workflow where the patient is about to collect their result. *(GAP-04, GAP-12)*
- **Patient notes are stored but not shown where they matter.** Notes render on the single-test result screen and as a column on the per-patient result sheet, but the profile and culture result-entry screens do not show them at all, and the delivery workflow cannot reach them. *(GAP-04, GAP-05)*
- **The account panel cannot refund, cannot clear, and cannot express a percentage discount.** The operation types are Payment, Correction and FullSettlement only. The reference's surcharge convention and two-press Enter rule are replaced by separate buttons. *(GAP-13, GAP-14)*
- **Patient-name search is partial-only and off by default.** The name predicate is a `Contains` test gated behind `EnablePatientNameSearchAssist`, whose seeded default is `false` — so in a default installation the search box does not match a patient's name at all. Card number and the not-delivered criterion are absent entirely. *(GAP-06, GAP-07, GAP-08)*

**Areas of demonstrated compliance.** The registration and test-selection workflow, the result-entry and review cycle, the receipt/invoice/envelope/barcode printing paths, the cash-movement and sent-out-samples accounting, the statistics module's four census sections, the user and attendance modules, and the settings persistence for report, receipt, envelope and system settings are all implemented and, where they could be executed, verified by passing tests.

**Unresolved questions.** 14 in-scope functions could not be classified with confidence. All of them carry a reference evidence status of *Unverified* or *Not shown* — the reference itself does not establish the required behaviour — so they are **not** counted as gaps. They are listed in §6 with the evidence that would resolve each.

**Verification limitations affecting confidence.** The WPF layer was compile-verified but never executed; the presentation test suite did not run; the live relational migration chain was not exercised because no Docker engine is available; and the audit is static plus test-suite based, not an end-to-end behavioural observation of the running application. These limits bound the confidence of every *Presentation-layer* conclusion in §4; they do not affect the Domain, Application or Infrastructure conclusions, which were exercised by 3,040 passing tests.

## 3. Scope and reference interpretation

### 3.1 How the canonical reference was read

The reference was read directly, in full, at the file identified in §1. Its own §3 defines six inventory levels (Function, Subfunction, Rule, UI element, Container, Output) and states the granularity policy explicitly: *"A screen is never counted as a function by virtue of being a screen"*, *"A column is not a function"*, and *"An entry whose evidence status is not Verified is not a gap: it is an open question"*. This report follows that policy rather than re-deriving it.

Its §16 global identifier registry was parsed mechanically to recover every identifier with its canonical name, source label, type, level, owning unit, evidence status and parity scope. That parse produced 1,787 rows — 1,715 inventory entries plus 72 group headers — and the level counts reproduce the reference's own §15.1 totals exactly (327 / 266 / 50 / 786 / 248 / 38 = 1,715), as do its 51 out-of-scope entries, its 30 *Unverified*, 17 *Not shown* and 9 *Sample* evidence statuses, and its 75 unresolved questions. This is the mechanism that makes the coverage accounting in §9 reproducible rather than asserted.

### 3.2 The functional assessment unit

The reference's §15.1 states that the behaviour-bearing population is *"the 327 functions, the 266 subfunctions and the 50 business rules"* and warns that comparing 1,715 inventory entries against an implementation *"will report a very large number of missing items, most of which are fields, columns and labels"*. This report therefore defines its counting unit as follows, and applies it consistently.

> **Functional assessment unit (FAU).** One canonical reference entry recorded at the reference's own *Function* level (§3 of the reference), which the reference defines as *"an independently identifiable behaviour that can be exercised and observed on its own"*. A UI element, a container, a rule, an output or a registry row is **not** a separate FAU.

Three reference areas required an explicit supplementary treatment, because the reference establishes their behaviour at UI-element level rather than at Function level. These are recorded as **supplementary assessments** and are **not** counted in the FAU population; they are reported in full in §4.5 so that none of the six explicitly in-scope areas is under-reported.

| Supplementary assessment | Anchored on reference identifiers | Why it is not an FAU |
|---|---|---|
| SUP-PWD — print-result password | 1.2.2.4.2, 1.2.2.4.2.1, 7.7.2 | The reference records the password as fields and an option, with no Function-level entry for it |
| SUP-NOTES — notes rendering | 1.2.2.4.1 and the 1.6.1.x notes/comment elements | The reference records the patient notes as a field; the notes *action* (1.4.1.4.6) is already an FAU |
| SUP-ACCT — account-panel elements and rules | 1.3.1.1–1.3.1.9, 1.3.1.4.1, 1.3.1.4.2 | The reference records these as fields and business rules; the account *actions* are already FAUs |

### 3.3 Reference uncertainty rules applied

The reference's own evidential qualifications were applied without exception and without improving or auditing its methodology:

- **Unverified** and **Not shown** entries were never converted into *MISSING*. Where the behaviour is absent but the reference does not establish it, the result is **UNDETERMINED** and the evidence needed to resolve it is stated.
- **Sample** entries (illustrations) were not read as rules.
- The reference's 75 consolidated unresolved questions (Q-001…Q-075) were read and used to explain *why* certain entries are Unverified, not to re-open them.
- Where the reference's §16 registry and its §2 exclusion list disagree, the disagreement is disclosed in §7 and the classification follows the exclusion *category*, not the registry's per-entry marking.

### 3.4 The five permanent exclusions

Exactly the five authorised categories were excluded, at the category level only:

1. **Online results portal ecosystem** — online results portal, online receipt printing, doctor/laboratory accounts, Android application
2. **Equipment management** — equipment, maintenance and calibration records
3. **Analyser integration** — blood/CBC analyser connectivity and result importing, including correction factors
4. **Multi-branch support**
5. **External results delivery** — SMS, e-mail and fax delivery of results

Exclusion was applied narrowly. No screen, workflow, module or technical layer was excluded because one aspect of it belonged to a category: the *samples sent outside* family, the *external entities and laboratories* family and the *contract price lists* family all remain in scope, as the reference's own §2 requires. The excluded items are listed and counted in §7 and are excluded from the gap register and the roadmap in §8.

### 5.1 Gap register in detail

#### GAP-01 — Print-result password is not enforced on any print or delivery path

- **Reference identifiers:** `1.2.2.4.2.1 (UI element)`, `1.2.2.4.2 (UI element)`, `1.6.1.3.3`, `1.6.1.7.2`, `1.2.2.6.6`, `1.2.2.6.7`, `1.4.1.4.11`, `7.7.2`
- **Current classification:** MISSING (enforcement)
- **Required behaviour:** The reference's Print Result Password Enable Option (1.2.2.4.2.1) is defined as 'Enables the password requirement for printing the result.' Once enabled, a result may be printed only after the correct password is supplied, and the receipt carries the password that gives access to the result (7.7.2).
- **Actual observed behaviour:** Top-Lab persists a print-result password (a hashed value in SystemSettings.PrintResultPasswordHash) and can verify it (PrintResultPasswordVerifier.Verify / PrintResultPasswordHasher.Verify), but the verifier is never invoked by any production path. A repository-wide search for 'PrintResultPasswordVerifier' returns only the DI registration in src/TopLab.Application/DependencyInjection.cs:44, the class declaration, and a unit test file. No result-entry, report-printing, receipt-printing, invoice-printing, envelope-printing or delivery path consults it. The requirement is therefore configured but never enforced.
- **Supporting repository evidence:**
  - `src/TopLab.Application/Features/SystemAndPrintSettings/Common/PrintResultPasswordVerifier.cs :: PrintResultPasswordVerifier :: 15-44`
  - `src/TopLab.Application/DependencyInjection.cs :: AddScoped<PrintResultPasswordVerifier> :: 44`
  - `src/TopLab.Domain/Settings/PrintResultPasswordHasher.cs :: PrintResultPasswordHasher :: 17-40`
  - `src/TopLab.Domain/Settings/SystemSettings.cs :: SetPrintResultPassword :: 82-93`
  - `src/TopLab.Infrastructure/Persistence/Configurations/SystemSettingsConfiguration.cs :: seed :: 30`
- **Impact / rationale:** A password that a user believes protects result printing protects nothing. The stored hash is never compared against anything, so the setting is a false assurance on a data-protection control that sits directly on printed patient results.
- **Proposed roadmap stage:** R2

### 5.2 How duplicate descriptions were consolidated

The gap register holds 30 gaps against 90 low-level reference identifiers. The consolidation rules applied were:

- One underlying defect affecting several reference identifiers produces **one** gap with all identifiers attached (for example GAP-12 carries the eight absent delivery actions; GAP-29 carries the eighteen absent settings controls).
- Distinct unmet requirements that happen to sit on one screen are **not** merged (for example GAP-11 filter bar versus GAP-13 refund versus GAP-14 discount rules are three separate gaps despite all touching the patient editor).
- A single defect that would generate several descriptions in different places is counted once (for example the absent print-password enforcement is one gap, not one per print command).
- Reference identifiers that are *UI elements* or *rules* are attached to the gap of the function they govern rather than counted as functions of their own.

## 8. Dependency-aware implementation roadmap

6 stages are proposed, in dependency order. The stages are ordered so that no stage depends on a later one: R1 and R3 are independent, R2 depends on R1 only for the patient-side placement of the password field, and R4, R5 and R6 are independent of one another.

| Stage | Title | Gaps | Dependency |
|---|---|---|---|
| **R1** | Patient registration, result entry, delivery and account action bands | 9 | — |
| **R2** | Per-patient print-result password and its enforcement | 3 | R1 |
| **R3** | Patient search criteria and the search action bar | 4 | — |
| **R4** | Main-window period list and the work-sheet module | 2 | — |
| **R5** | Reference-data editing: undo, group membership, deletion semantics and history | 6 | — |
| **R6** | Utilities, statistics, auditing, sent-out samples, sample withdrawal and settings | 6 | — |

### 8.1 Why the stages are grouped this way

- **R1** groups the action-band work because the reference's action bands are a single design idea repeated across the registration, result-entry, delivery and account screens. Doing them together keeps one navigation and command convention rather than four, and lets the shared delivery/result surfaces be changed once.
- **R2** is separated from R1 because it is a single, self-contained data-protection capability that must be correct on its own terms, and because the reference places the password on the patient record — a change to the same screen R1 edits, which is why it follows R1.
- **R3** is separated because the search screen and its query have their own semantics (AND-combined guards, tri-state filters, paging) and because the reference's criteria live in a different place from where Top-Lab's currently do.
- **R4** groups the two modules whose gap is that a *reference screen mode* is missing or disabled — the period list and the work-sheet's group mode — because both are about which rows a screen shows rather than about what a button does.
- **R5** groups the reference-data editing rules because they share one answer: how Top-Lab behaves when a user abandons or reverses an edit. Changing that answer in six places separately would produce six inconsistent behaviours.
- **R6** groups the remaining, lower-frequency modules. They are grouped only to keep the roadmap to a workable number of stages, not because they are technically related.

### R2 — Per-patient print-result password and its enforcement

- **Associated confirmed gaps:** GAP-01, GAP-02, GAP-03
- **Canonical reference identifiers covered:** 1.2.2.4.2, 1.2.2.4.2.1, 7.7.2, 1.6.1.3.3, 1.6.1.7.2, 1.2.2.6.6, 1.2.2.6.7, 1.4.1.4.11
- **Required behaviour and rationale:** Make the print-result password a per-patient value with a per-patient enable flag, enforce it on every path that produces or releases a result (report printing, receipt printing, invoice printing, envelope printing, bulk print and the delivery screen's own print path), and print it on the receipt as the credential that gives the patient access to their result.
- **Evidence establishing the need for change:** The verification machinery already exists and is already unit-tested — PrintResultPasswordHasher hashes, PrintResultPasswordVerifier verifies — but the verifier has no production call site (its only non-test references are the DI registration and the class itself), the password is a single global setting on the SystemSettings row, and the receipt projection carries no password at all. The reference's own enable option states the requirement in terms: it 'Enables the password requirement for printing the result'.
- **Dependencies:** R1 for the patient-side placement (the reference puts the password in the patient registration screen's Notes and Communication Block, so the field is added to the screen R1 already edits). The enforcement and receipt work itself has no dependency on R1.
- **Likely affected layers, modules, entities, services, persistence definitions, WPF components and tests:** Domain: Patient (password hash, enable flag); Application: SystemAndPrintSettings (an enforcement service that reuses PrintResultPasswordVerifier rather than adding a second one), PatientBilling (receipt query and print handler), ReportProduction (report print handlers), PatientEnvelope (envelope print handler), ResultsEntry (bulk print handler); Presentation: PatientEditorView (the per-patient field in place of the global block), a password-prompt dialog modelled on the existing SystemMenuPasswordDialog, and the print entry points. Tests: extend PrintResultPasswordVerifierTests to cover each enforcement call site.
- **Database migration:** **REQUIRED. The reference defines the password as a per-patient field on the patient record (1.2.2.4.2) and requires it to be printed on the receipt (7.7.2); a per-patient password therefore needs a persisted hash and enable flag on the patient, and the receipt projection needs the password value. The existing SystemSettings columns may be retained as a laboratory-wide default. As listed in GAP-01, GAP-02 and GAP-03.**
- **Acceptance criteria:** Enforcement must preserve the application's ability to operate fully without an external internet connection: the prompt, the hash comparison and the receipt rendering are all local operations, and no new network dependency may be introduced.
- **Unresolved questions and assumptions:** Printing a plaintext password on the receipt is a direct consequence of the reference (7.7.2: 'The password that gives access to the result is printed on the receipt'). This should be confirmed with the product owner before implementation, because the reference requirement and ordinary data-protection practice point in opposite directions. If it is rejected, GAP-03 should be recorded as an accepted deviation rather than implemented as specified.
- **Material risks and sequencing constraints:** Whether a laboratory-wide default password should remain alongside the per-patient one is not established by the reference. The reference places the field on the patient, so the migration should add the per-patient columns without dropping the existing SystemSettings columns, and the behaviour for a patient with no password set must be decided explicitly rather than inherited from the current global default.

## 9. Coverage and classification totals

### 9.1 Counting rules

1. **The counting unit is the functional assessment unit (FAU)** defined in §3.2: one reference entry recorded at the reference's own *Function* level. UI elements, containers, rules, outputs and registry rows are not counted as functions.
2. **A parent and its children are not counted independently** unless the reference establishes them as distinct functional units. The reference's own §3.1 policy — *"Where a parent has several materially distinct children, the parent is recorded and the children are recorded"* — is applied: a parent function with decomposed children is assessed once, at the level of its children, and the parent's identifier is retained alongside them.
3. **Several identifiers that describe one functional requirement are assessed together**, and all identifiers are preserved in the assessment record. Where the reference establishes the behaviour only at UI-element or Rule level, it is reported as a supplementary assessment (§4.5), not as an extra function.
4. **One defect affecting several identifiers yields one gap.** A gap count is a count of independently actionable unmet requirements, not of reference identifiers.
5. **Several genuinely distinct unmet requirements are not merged**, even when they affect one screen.
6. **Excluded items and UNDETERMINED items are counted separately from confirmed gaps** and never contribute to the gap count.
7. **Percentages use the FAU population as the denominator** and never mix it with the inventory-entry population.
