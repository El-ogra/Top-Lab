## 2. Settled decisions (formerly open decisions OD-4, OD-5, OD-6, OD-8, OD-9)

The project owner has reviewed every open decision in the V2 draft and **approved the V2 recommended option in each case without exception**. Each decision below is now a **settled, confirmed fact**, not an open choice. They are recorded here for traceability and are encoded directly in the relevant slices, message tables, and rules.

### 2.1 OD-4 — How M02 honors `SystemSettings.DefaultAccountType` and the referral-entity default placeholder

**Settled choice (V2 Option 1 — approved).** **M02 reads `SystemSettings` directly via the existing `IApplicationDbContext` and uses M14's `ReferralNameResolver` for the referral-entity default.** No new port, no new interface, no new permission. Specifically: M02's `GetRegistrationCatalogQueryHandler` issues a `GetSystemSettingsQuery` (intra-Application MediatR) — this is a non-coupling read against an already-shipped M22 query — and calls `ReferralNameResolver.Resolve(null, sex)` directly for the two placeholders.

**Encoded in.** M02-S2 `GetRegistrationCatalogQuery` (§5.2). The handler exposes `AccountType DefaultAccountType` (read from the M22 `SystemSettingsDto`) and `string ReferralPlaceholderMale` / `string ReferralPlaceholderFemale` (computed by calling `ReferralNameResolver.Resolve(null, Sex.Male)` / `.Resolve(null, Sex.Female)`).

### 2.2 OD-5 — Patient phone-number handling at M02 (FR-M02-003)

**Settled choice (V2 Option 3 — approved).** **`CreatePatientCommand` and `UpdatePatientCommand` both carry the full `IReadOnlyList<PatientNumberInput>`.** The handler uses a new `Patient.SetPhoneNumbers(IEnumerable<(string, byte)>)` mutator (added in M02-S1) which clears the backing list and re-populates it inside the domain, preserving the FR-M02-003 invariant that all stored numbers are non-empty after trim.

**Encoded in.** M02-S1 `Patient.SetPhoneNumbers` mutator (§5.1); M02-S3 `CreatePatientCommand` / `UpdatePatientCommand` shapes (§5.3); the existing `PatientPhoneNumber.Create` factory's `string.IsNullOrWhiteSpace` guard is the only code-grounded rule (no invented validation).

### 2.3 OD-6 — Sample-type flags and "Taken Outside Lab" handling at M02 (FR-M02-008)

**Settled choice (V2 Option 1 — approved).** **M02 carries the five sample-type flags and `IsTakenOutsideLab` in `AddTestsToVisitCommand` (per test) and on `UpdatePatientTestSampleFlagsCommand`.** A new `PatientTest.UpdateSampleFlags(bool, bool, bool, bool, bool, bool)` mutator is added to the Domain in M02-S1. The flag is **per-test**, faithful to the `RLS_Learn.pdf` §1 wording "خانة التحليل المسحوب خارج المعمل أسفل قائمة التحاليل".

**Encoded in.** M02-S1 `PatientTest.UpdateSampleFlags` mutator (§5.1); M02-S3 `AddTestsToVisitCommand` and `UpdatePatientTestSampleFlagsCommand` shapes (§5.3); the M21 `MarkSampleDrawnCommand` (in M21's own plan) rejects redrawing an outside-drawn test with the message `"تم تسجيل العينة كمسحوبة خارج المعمل؛ لا يمكن تعديلها من شاشة السحب"`.

### 2.4 OD-7 — M21's list-of-pending-samples query shape

**Settled choice (V2 Option 1 — approved).** **Two queries: `GetPatientsWithUncollectedSamplesQuery` and `GetPatientTestsForDrawQuery`.** The patient list is a distinct shape from M02's `SearchPatientsQuery` (which is name/phone search, not "patients with un-drawn tests today"). Faithful to the `RLS_Learn.pdf` §8 wording "نختار المريض المراد سحب عيناته من قائمة المرضى على يمين النافذة فتظهر العينات المراد سحبها".

**Encoded in.** M21-S1 of M21's plan: `GetPatientsWithUncollectedSamplesQuery` returns a list of `PatientWithUndrawnTestsDto`; `GetPatientTestsForDrawQuery` returns `Drawn` and `NotDrawn` lists for a patient. (M21 is a separate plan; M02 only needs to know that the (PatientId, IsSampleDrawn) index it adds in M02-S1 is consumed by M21's query.)

### 2.5 OD-8 — Permission code for M02/M21 writes (V2 correction to V1)

**Settled choice (V2 Option 1 — approved).** **Reuse the existing `ADD_EDIT_PATIENT` (id 1) and `DELETE_PATIENT` (id 9) codes already seeded in `PermissionConfiguration.cs`.** No new seed row, no new ADR debate. M02's `CreatePatient`, `UpdatePatient`, `AddTestsToVisit`, `UpdatePatientTestSampleFlags`, `AddMedicalCondition`, `RemoveMedicalCondition`, `ClearAllTests`, and `RemoveTestFromVisit` all carry `RequiredPermissionCode => "ADD_EDIT_PATIENT"`. `SoftDeletePatient` carries `RequiredPermissionCode => "DELETE_PATIENT"`. M21's `MarkSampleDrawn` and `MarkAllSamplesDrawnForPatient` (in M21's own plan) also carry `RequiredPermissionCode => "ADD_EDIT_PATIENT"` (the phlebotomist's role is the same operational write as the registrator's).

**Encoded in.** All M02-S3 commands (§5.3), the `PatientRegistrationAccessPolicy` constants introduced in M02-S2. **No `PermissionConfiguration` change in this plan.**

### 2.6 OD-9 — ID generation for `Patient.PatientId` and `LabId`

**Settled choice (V2 Option 3 — approved).** **EF Core identity for `PatientId` (the `int` identity column); `LabId` is user-supplied and applied via the existing `Patient.AssignLabId` mutator if present.** No new port, no `IPatientIdGenerator`.

**Encoded in.** M02-S3 `CreatePatientCommandHandler` calls `Patient.Create(PatientId.Create(0), ...)`; EF Core assigns the value on save; the response DTO carries the saved `PatientId`. `LabId` is passed to `Patient.AssignLabId(...)` when present.

#### 3.1.5 The M13 zero-migration outcome

M13 adds **no new EF Core migration**. All tables/columns/FKs needed by M13 already exist from the F5 baseline (the M13 baseline migration `20260828052248_BaselineDataModel.cs` creates all M13 tables; the `ApplicationDbContextModelSnapshot.cs` matches the M13 configurations; a model-vs-snapshot zero-drift gate runs in M13's own Infrastructure slice).
