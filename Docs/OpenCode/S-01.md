## 1. Executive Summary

S-01 delivers the Patients workstream: a Patients hub reachable from the shell's «المرضى» button, and the unified "Add/Edit Patient Data" screen combining patient demographics, test ordering with sample-type flags, a live billing panel, and four working print actions (barcode label, worksheet, receipt, invoice). The backend for registration, ordering, and billing is already Done (M02/M03 — audit §7 READY); what is missing is the entire printing document layer (barcode service, receipt/worksheet/invoice renderers — audit §E.3 NOT FOUND) and the entire Presentation layer (audit §B.3 NOT FOUND, §A.3 fall-through).

**Slicing:** 6 slices, backend-first, UI-last:

| # | Slice | Layer | Blocks |
|---|---|---|---|
| S1 | Barcode service (`IBarcodeService` implementation, Code-128, printer routing) | Backend | S6 barcode button |
| S2 | Receipt printing (`IReceiptPrintingService` port + impl + `PrintReceiptCommand`) | Backend | S6 receipt button |
| S3 | Invoice concept + renderer (`InvoiceIssue` record, DTO, query, `IInvoicePrintingService`, `PrintInvoiceCommand`) | Backend (+migration) | S6 invoice button |
| S4 | Visit worksheet renderer (`GetVisitWorkSheetQuery` + worksheet PDF + `PrintWorkSheetCommand`) | Backend | S6 worksheet button |
| S5 | Patients hub + «المرضى» navigation wiring | Presentation | S6 entry point |
| S6 | Unified Add/Edit Patient Data screen (demographics + ordering + billing + 4 print actions) | Presentation | — (final) |

**Sequencing rationale.** Backend printing slices come first because the binding owner decision forbids shipping the screen with any stubbed button: S6's four print buttons can only be wired against existing services. S1–S4 are mutually independent (different printers, different documents, different ports) but are ordered by ascending conceptual risk: S1 is the smallest (port exists, single string payload); S2 follows the M-22 `ReportPrintingService` pattern most closely; S3 carries the only new domain concept and the only migration; S4 reuses the S2/S3 rendering machinery decided earlier. S5 (hub + navigation) precedes S6 so that S6's screen has a reachable entry point the moment it lands — the hub ships with its «إضافة وتعديل بيانات المرضى» button disabled until S6 enables it (see Settled Decisions — disabled-by-design is the repo's established placeholder idiom, not a half-wired button). Within S6, no internal split is possible without shipping a dead panel.

**No half-wired states (binding constraint, restated).** Every UI button visible and enabled in the final screen has a complete backend path by the end of S6: each print button → MediatR command → Application port → Infrastructure renderer → `PrinterAssignment` routing → `IPdfPrinterDispatcher`. Any button whose backend cannot exist yet (the hub's three other actions) ships disabled (`IsEnabled=false`), matching the existing `NavigationItem.IsEnabled` shell idiom and the disabled Home-placeholder buttons at `MainWindow.xaml:64–74`.
