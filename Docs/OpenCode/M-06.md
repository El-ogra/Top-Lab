## 5. Module 6 — Culture & Sensitivity Result Entry (backend only)

> Self-contained plan. **All of this module's rules are settled requirements:** culture-entry is restricted to the culture test's **attached antibiotic list** (UI Blueprint S-11 + FR-M06-002 + Data Model §6.4 FK-to-catalog + FR-M15-002 escape hatch + ADR-0031); the display filter is an entry-time display concern only — recorded facts are never hidden (S-11 note + ADR-0031); the child signal is fully documented (`CultureAntibioticDisplay.ChildAgeThresholdYears = 12`, strictly under 12 — ADR-0031 + FR-M15-004); the print-time balance block (Data Model §13 BR-07 + Reporting §9 + FR-M09-003); printability requires verification (Reporting §9); no `PatientTest.IsDeleted` (Data Model §6.1/§2 + ADR-0018); **the physical storage of the pregnancy indication (settled by the owner): a genuine new enumerated value `Pregnancy = 2` is added to the existing `MedicalConditionCategory` list, and the pregnancy indication is a `MedicalConditionType` row named «حمل» (Pregnant) whose `Category` is `Pregnancy`, attached to the patient via the existing `PatientMedicalCondition` join — the indication is read structurally from the category value, never from name-matching**; **the entered-invariant mechanism (settled by the owner): the dedicated `PatientTest.MarkEntered(int, DateTime)` mutator, identical to the profile module's contract**. Feature folder: `CultureResults`.

### 5.1 Module 6 context — what exists and what is assumed (inlined)

- **Existing at `70f145e` (re-verified):** `CultureResult` (`src/TopLab.Domain/Results/CultureResult.cs` + configuration) — **1:1 with `PatientTest`, PK = `PatientTestId`**; all-nullable `Sample` (≤100), `OrganismA/B/C` (≤150), `CultureCondition` (≤200), `ColonyCount` (≤50); **public constructor** `(patientTestId, sample=null, …)`; **no `Update` mutator**; FK `CultureResult → PatientTest` Cascade (`HasOne<PatientTest>().WithOne()`). `CultureAntibioticResult : Entity<CultureAntibioticResultId>` — `PatientTestId`, `AntibioticId`, `SensitivityCategory { HighlyFor=0, ModerateFor=1, LowFor=2, ResistantFor=3 }` (tinyint); static `Create` only; identity PK; **FK `→ CultureResult` Cascade on the shared `PatientTestId` key; FK `→ Antibiotic` Restrict**; index on `PatientTestId`. `CultureAntibioticAttachment` (composite PK `TestId+AntibioticId`, no DB FK on the join per the M15 ADR-0031). `Test.IsCultureType`, `Test.ResultKind.Culture = 2`. M15's shipped surface (re-verified): `GetCultureAntibioticsQuery` → `CultureAntibioticListDto(int TestId, string TestName, int AttachedCount, IReadOnlyList<AttachedAntibioticDto> Antibiotics)`; **`CultureAntibioticDisplay.IsDisplayable(isPregnancyFlagged, isChildrenFlagged, isPregnancyIndicated, isChildUnder12)` = `(!preg && !child) || (preg && pregIndicated) || (child && childUnder12)`** with **`ChildAgeThresholdYears = 12`** (both verbatim, same Application assembly — this module calls the helper directly); `AntibioticDto(int Id, string Name, bool IsPregnancyFlagged, bool IsChildrenFlagged)`, `AttachedAntibioticDto(int AntibioticId, string Name, bool IsPregnancyFlagged, bool IsChildrenFlagged)`. `MedicalConditionType` — `Name`, `Category { Medication=0, Condition=1 }` (re-verified — gains `Pregnancy = 2` in this module, per the owner's settled decision). `PatientMedicalCondition` join exists in schema.
- **Settled entry model (inlined):** the entry surface is the **attached antibiotic list** (UI Blueprint S-11: the screen's key controls are the "Attached antibiotic list", the four sensitivity classifications, and the display toggles; its note adds the list is filtered by the Pregnant/Children flags against the patient's data). FR-M06-002: antibiotics are entered by double-clicking from the presented list (or select + «Add») into the four classifications — selection from a list, not free text. Data Model §6.4: `CultureAntibioticResult.AntibioticId` is an FK to the `Antibiotic` catalog — free-text names on results are structurally rejected. An antibiotic missing from the list is first created/attached through the M15 configuration surface (FR-M15-002: typed manually there, then Save). ADR-0031: M15 deliberately ships the attachment contract for this module to consume ("The display filter at result entry (BR-12) is the M06 consumer's concern").
- **The settled pregnancy signal (inlined in full — settled by the owner as a structural, enumerated storage):** the pregnancy indication is documented as patient-level data (FR-M15-003: an antibiotic flagged «Pregnant» appears only "when pregnancy is indicated in the patient's data"; BR-12; Data Model §13 BR-12 mapping: filtered against "Patient sex/pregnancy indication and age at query time"). **Physical storage (settled by the owner):**
  1. The existing `MedicalConditionCategory` enum (`src/TopLab.Domain/Common/Enums/MedicalConditionCategory.cs`, currently `{ Medication=0, Condition=1 }`) gains **`Pregnancy = 2`** — a genuine new enumerated value (code-only change; the column is a tinyint, so **no migration**).
  2. The pregnancy indication for a patient is a **`MedicalConditionType` row whose `Category == MedicalConditionCategory.Pregnancy`, named «حمل» (Pregnant)**, attached to the patient through the existing `PatientMedicalCondition` join (M02's `AddMedicalCondition`/`RemoveMedicalCondition` mutators and `AddMedicalConditionCommand`/`RemoveMedicalConditionCommand` already provide the writable path, and M02's `GetMedicalConditionTypesQuery` already exposes the catalog to the registration screen).
  3. `isPregnancyIndicated` for the display filter is computed **structurally**: `patient.MedicalConditions.Any(mc => mc.Type.Category == MedicalConditionCategory.Pregnancy)` — never by name-matching.
  4. **Seed obligation (this module's Slice 1):** a configuration-side `HasData` seed (or the seeding mechanism the M12–M17 modules already use for catalog rows — reconfirm the exact mechanism at execution and mirror it) inserts the «حمل» `MedicalConditionType` row with `Category = Pregnancy`, so the value exists in every environment with no manual DB edit. If the seed mechanism requires a migration for the catalog row, that migration is added and flagged in Slice 1 (the enum change itself needs none).
  5. The display filter affects **entry-grid display only** — recorded results are never hidden and writes are never blocked by it (settled: S-11 note + ADR-0031).
- **Assumed from M02 (inlined):** `Patient.AddMedicalCondition/RemoveMedicalCondition` exist and the join rows are queryable via `IApplicationDbContext`; `Patient.IsDeleted` exists; the fake gains `PatientMedicalCondition`/`MedicalConditionType` lists (M02 adds them — if absent at execution, this module's Slice 2 adds them; one-line contingency).
- **Assumed Domain contract on `PatientTest` (inlined verbatim; same ownership matrix as the profile module):** `MarkEntered(int, DateTime)` (sets `EnteredByUserId`/`EnteredAtUtc` only; throws `InvalidOperationException("Result is reviewed; unreview first.")` when `IsReviewed`), `Unreview()` (throws `InvalidOperationException("Printed or delivered results cannot be un-reviewed.")` when `IsPrinted || IsDelivered`), and the guard contract (`MarkReviewed` requires entered; `MarkPrinted` requires reviewed; `EnterResult` rejects when reviewed). **First-shipper rule applies verbatim** (if absent at execution, this module's Slice 1 adds them with exactly these shapes and records it in the ADR).
- **Balance formula (settled — inlined in full, per independence):** `TotalCharged = Σ PatientTest.PriceAtOrderTime + Σ (PaymentOperation.Amount where !IsVoided && IsExtraCharge)`; `TotalPaid = Σ (PaymentOperation.Amount + coalesce(DiscountAmount, 0) where !IsVoided && !IsExtraCharge)`; `Balance = TotalCharged − TotalPaid` (negative = credit; `Correction` = credit on paid side; `FullSettlement` = ordinary payment; voided ignored). This module ships its own private `Common/BalanceProbe.cs`.
- **This module does not** manage the antibiotic catalog or attachments (M15 owns them, already shipped, writes gated on `EDIT_SYSTEM_SETTINGS` — this module only reads).

### 5.8 Module 6 — Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The «حمل» catalog row is deleted or renamed by an administrator | The signal reads `Category == Pregnancy`, not the name — renaming is harmless; deletion is an admin action on a catalog row (same exposure as any catalog row); the ADR records the row's purpose so the admin-catalog wave treats it as reserved. |
| No shipped screen lets an admin set `Category = Pregnancy` on a new type | The seeded «حمل» row covers the documented use case with zero CRUD gap (a genuine enumerated value the owner can attach to patients immediately via M02's shipped `AddMedicalConditionCommand`); if additional pregnancy-category types are ever needed, the admin-catalog wave adds the CRUD — recorded in the ADR. |
| Attachment list edited (M15) after results recorded | Facts-never-hidden rule keeps saved rows visible in grid + report; write-side attached-only check runs against the *current* attachment set at each save (stated rule — detaching an antibiotic with recorded results is M15's guard to manage; M15's shipped `DeleteAntibiotic` already blocks on recorded results per its message table). |
| First-shipper collision on `MarkEntered`/`Unreview` | Identical inlined signatures + drift checks in the consuming modules (ownership matrix). |
