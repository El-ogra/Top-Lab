## 1. Execution Philosophy (repo-native loop-engineering)

This programme follows the repository's established loop-engineering methodology (as demonstrated in `Docs/OpenCode/Execution-Prompts.md`, `S-00.md`, `S-01.md`, and the M-xx/M-xx-memory.md pairs):

- **Two-artifact shape:** this plan (`S-02.md`) + the loop memory (`S-02-memory.md`). The memory file is the persistent execution state; the plan is the requirements surface.
- **10-stage cycle per slice:** (1) Pre-Execution Verification → (2) Deep Understanding → (3) File Analysis → (4) Planning → (5) Execution → (6) Post-Execution Verification → (7) Validation Gate → (8) Documentation Update → (9) Memory Status Update → (10) Git Commit (local only).
- **Quality gate (non-negotiable):** a slice is complete ONLY when (a) its implementation is fully complete per this plan + the P1 plan, (b) the ENTIRE solution builds with zero errors AND zero warnings (`dotnet build TopLab.sln`), (c) ALL existing automated tests pass (`dotnet test TopLab.sln` — full suite, not just affected tests), (d) the slice's own Validation Gate passes with concrete evidence.
- **Evidence over claims:** "implemented" is never evidence. Evidence = build output, test output, grep/diff gates, file inspection, and (for UI, where no UI test harness exists in the repo) an explicit manual-verification checklist with its result recorded — never invented.
- **Stop rule:** the SAME failure (a specific build error, file-edit failure, or test failure) occurring **5 CONSECUTIVE** times → STOP entirely and write a Stop Report in the memory file. Ordinary expected test failures resolved within the same correction cycle do not count.
- **Git policy:** automatic LOCAL commit after each verified slice on the CURRENT branch (`main`); NEVER create a branch, NEVER push, NEVER rewrite history. Commit format: `[S-02] Slice N/8: <slice title> — loop-engineering`.
- **No half-wired states (binding, per S-01 precedent):** every enabled control ships with a complete backend path; anything whose backend cannot exist yet ships disabled, matching the existing `NavigationItem.IsEnabled` placeholder idiom.
- **Preserve existing behaviour:** no change unless the P1 plan explicitly requires it. No broad rewrites, no unrelated cleanup, no speculative abstractions, no future-proofing.
- **The P1 plan is authoritative for requirements.** This document assigns scope/order/gates; for field lists, validation messages, state behaviour, and screen specs it cites the P1 plan section (e.g. "P1 §4.4.2") rather than duplicating hundreds of lines. Verbatim Arabic messages quoted below are binding.

## 4. Programme-Level Rules (apply to every slice)

1. **Order:** 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7, strictly sequential; no parallel slices, no skipping, no reordering.
2. **Zero-drift:** no EF migration is authorised in P1. If code inspection ever suggests one is needed, STOP and report — do not silently migrate.
3. **Scope confinement:** each slice's diff is confined to its listed surface plus its documented dependency touches. Anything beyond that must be recorded in the memory file with justification, or reverted.
4. **Verbatim messages:** Arabic strings quoted in this plan and in the P1 plan are binding — exact wording, no paraphrase.
5. **Confirmed vs spec:** where the P1 plan tags an item Confirmed-from-code, the implementation must use that exact artifact (command/query/DTO/validator). Where tagged «مواصفة خطة», implement as specified. Where tagged Uncertain, resolve from the actual code and record the resolution — never invent.
6. **Unresolved owner decisions that MUST remain unresolved** (build around them, never silently decide): About-screen final copy (placeholder); missing `ReactivateAnalyte`/`DeleteAnalyte`/`DeleteProfile` (no affordances); price-list printing (no control).
7. **Settled owner decisions (final — do not reopen):** D1 (LabPrintText tab inside `SystemSettingsView`), D3 (M14 entry under «الحسابات» + temporary Settings route + direct picker), D6 (block delete of attached antibiotics with the exact message), D7 (self-change-password dialog from the status bar, new command authorised), D9 (immediate attach/detach, no bulk save).
8. **Stop rule:** 5 consecutive identical failures → Stop Report in the memory file and halt. Also stop on: a genuinely unresolved owner decision blocking progress, a destructive/irreversible action not authorised by this plan, or information only the owner can supply. Never stop with "shall I continue?" when the next action is defined and reversible.
9. **Completion of the programme:** all 8 slices committed locally → emit a brief summary and stop. P1 is then done; P2–P5 are out of scope.
