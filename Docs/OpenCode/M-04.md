## 3. Module 4 — Results Entry & Result Lifecycle (backend only)

> Self-contained plan. **All of this module's rules are settled requirements:** the seven-state patient aggregate status and its aggregation rule (PRD §8.2/§8.3 binding + BR-01 + ADR-0015 + Test Strategy §3.1 — `PatientStatusCalculator` is implemented in full in this module, no stub, no waiver); the print-time balance block (per-user `BlockPrintOnRemainingBalance` + computed balance → `Forbidden`/`Conflict` before printing — Data Model §13 BR-07 + Reporting §9 + FR-M09-003); auto review-and-completion as a system action when `SystemSettings.AutoReviewAndComplete` is set (FR-M22-008 + PRD §8.4 binding + Test Strategy §7.2-M04); auto-compute of `ResultFlag` at entry and persistence of the reference-range freeze with an explicit user-refresh path (Data Model §6.1/§13 BR-05 + Coding Standards §7.3 binding + BR-05 + FR-M04-008 + Test Strategy §7.2-M04); printability requires verification (Reporting §9 — the Finished stage alone is insufficient); no `PatientTest.IsDeleted` (Data Model §6.1/§2 + ADR-0018); **the edit-lock policy (settled by the owner): free re-entry until reviewed; after `IsReviewed`, entry rejects with `Conflict` and only a user holding `REVIEW_RESULTS` may un-review-then-re-enter via a dedicated `UnreviewResultCommand`**; **the reference-range snapshot storage mechanism (settled by the owner): a dedicated child table `PatientTestReferenceRangeSnapshots` keyed 1:1 by `PatientTestId`, carrying the full `ReferenceRangeSnapshot` record shape verbatim — the module's only migration**; **the overlapping-range selection rule (settled by the owner): most-specific range wins — a sex-matched row is preferred over a sex-null row, then the narrowest age band, and a true tie is broken by the lowest id (oldest row)**. - **The settled seven-state status model (inlined in full — PRD §8.2/§8.3, binding; BR-01; ADR-0015; Test Strategy §3.1):** the seven patient-level statuses are **S1 New** (patient newly registered; no result yet entered for any requested analysis), **S2** (one or more results not yet entered), **S3** (results entered but not yet reviewed), **S4** (entered and reviewed but not yet printed), **S5** (printed but not yet delivered), **S6** (all results delivered but an outstanding financial/account balance remains), **S7** (entered, printed, delivered, account fully settled). No additional statuses may be introduced; none may be removed. Each analysis maps to a stage by its earliest outstanding action (1 entry-pending→S2 · 2 review-pending→S3 · 3 print-pending→S4 · 4 delivery-pending→S5 · 5 settlement-pending→S6 · 6 complete→S7), and **PatientStatus = state(min over all per-analysis stages AND the account condition)** — the earliest incomplete stage / highest-priority outstanding action, in lifecycle precedence order (never by calendar date or record creation; a completed analysis must never hide an unfinished one). The S6 account condition is evaluated **only when no analysis is at stages 1–4** (all results delivered): a patient with an undelivered analysis AND an outstanding balance shows **S5** (delivery precedes settlement). S1 applies exactly when the patient is newly registered and no result has been entered for any requested analysis; as soon as the registration is no longer new while results remain unentered, the patient shows **S2**. Binding worked example: stages {3, 4, 1} → **S2**. Implementation: a **stateless Domain Service** (`PatientStatusCalculator`), never stored, never cached (ADR-0015); every consumer obtains the status through this single calculation.
  - *Stated micro-pin (documented as undocumented sub-detail):* §8.3's "newly registered" boundary for S1-vs-S2 is not operationally defined in `Docs/Source/`. This plan pins: **S1 applies iff no analysis has `EnteredAtUtc` set AND the patient's `RegistrationDateUtc` falls on the current UTC day** (registration "today" = new); otherwise unentered ⇒ S2. Recorded in the close-out ADR.
  - *Stage mapping onto the shipped columns (stated):* entry stage from `EnteredAtUtc`; review from `IsReviewed`; print from `IsPrinted`; delivery from `IsDelivered`; the account condition from the injected `balance` parameter (the calculator's existing signature `Calculate(Patient, IReadOnlyList<PatientTest>, decimal balance)` is sufficient as-is).
- **Assumed from M02/M21 (inlined):** `Patient.IsDeleted` exists; `PatientTest.UpdateSampleFlags` exists; M02 `RemoveTestFromVisit`/`ClearAllTests` already refuse removal once `EnteredAtUtc` is set (so this module never faces a removed-with-result row); M21 marks samples drawn. **This module does NOT require `IsSampleDrawn` before entry** — results for outside-drawn samples (`IsTakenOutsideLab = true`) are never drawn in-lab by definition, so entry is allowed regardless of draw state (stated rule).
- **Balance formula (settled — inlined in full, per independence):** `TotalCharged = Σ PatientTest.PriceAtOrderTime + Σ (PaymentOperation.Amount where !IsVoided && IsExtraCharge)`; `TotalPaid = Σ (PaymentOperation.Amount + coalesce(DiscountAmount, 0) where !IsVoided && !IsExtraCharge)`; `Balance = TotalCharged − TotalPaid` (negative = credit, no clamping; `Correction` rows contribute to `TotalPaid` as credits; `FullSettlement` rows as ordinary payments; voided rows ignored). This module implements this as a **private helper inside the ResultsEntry feature** (`Common/BalanceProbe.cs`) reading via `IApplicationDbContext` — it does not reference any other feature folder (independence rule).

### 3.1.1 Owner decisions accepted after the initial plan (binding)

- **D1 — registration requires an analysis.** A new patient is never persisted unless at least one analysis is selected. The non-Presentation enforcement boundary is the Application transaction: extend `CreatePatientCommand` with the same ordered-test inputs used by M02 and have its handler validate, resolve prices, create the `Patient` and one-or-more `PatientTest` rows, then save once. The existing later `AddTestsToVisit` remains the edit-existing-visit operation. Empty selection is a Validation failure; this does not alter the seven-state model (a newly persisted patient has requested analyses and is S1/S2 by the settled UTC-day rule).
- **D2 — local PDF export.** M04 delivers non-Presentation export of the patient's complete eligible P-01 result report to a caller-supplied **absolute local/LAN PDF path**. It reuses the canonical report model/layout settings, includes every reportable result flavor available in the data (simple, profile and culture) and uses the frozen reference snapshots where applicable. It is gated by `PRINT_RESULTS`; it requires the same verified-result eligibility as printing, but has no balance gate, does not print, does not increment `PrintCount`, and does not advance review/delivery/status. On successful write only, mark every `PatientTest` included in that exported report with `MarkExported(_dateTime.UtcNow)` and save. A pre-existing target file returns `Error.Conflict` and is never overwritten; invalid/non-absolute paths are Validation failures; I/O/PDF-rendering failures are `Unexpected` and leave export flags unchanged. The Application port owns PDF generation/writing; Infrastructure implements it; Presentation later only chooses/passes the path. No export-specific permission seed or migration is added.
- **D3 — bulk reprint decision.** Bulk print is a patient-report operation. Its deterministic two-step Application contract first returns the patient report candidates and whether a candidate contains any previously printed included `PatientTest`; Presentation must ask exactly `لقد تم طباعه هذا التقرير لهذا المريض من قبل هل ترغب في اعاده الطباعه` for each such candidate, then submits explicit per-patient confirm/cancel decisions. Confirm invokes the ordinary print path again (including permission, verified eligibility, balance block and `PrintCount`/last-print audit update for included rows); Cancel emits a skipped outcome and continues with later patients. First-time reports need no confirmation. Modified versus unchanged reports are both "previously printed" when an included row has `IsPrinted`; neither review/delivery state nor the balance/absolute-permission rules are bypassed. Reprint is intentionally non-idempotent because its audit count must increase.
- **D4 — simple result required value.** `EnterResultCommand` validates `ResultValue` before any persistence or lifecycle action: null, empty, and whitespace-only values fail Validation with exactly `الرجاء إدخال قيمة النتيجة قبل الحفظ`. Non-whitespace numeric and symbolic values remain valid. The guard belongs in the simple-result Application command (profile/culture retain their dedicated entry surfaces); `ClearResult` remains the explicit way to remove an existing unreviewed simple result.
- **D5 — authoritative balance calculator.** `BalanceProbe` is a thin ResultsEntry data loader only: it loads the patient’s ordered prices and payment operations and delegates the calculation exclusively to `TopLab.Domain.Billing.PatientAccountCalculator.Balance`. It must not reproduce the formula. This is inward-safe because Application already depends on Domain; no cross-feature dependency or adapter is required.

### 3.8 Module 4 — Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The S1/S2 "newly registered" boundary pin is an engineering choice on top of binding text | Pinned once (context section above), unit-tested both sides, recorded in the close-out ADR; flipping the pin is a one-line change in `PatientStatusCalculator` + one test row. |
| Overlapping reference ranges pick a surprising range | The selection rule is settled by the owner (most-specific wins: sex-matched preferred, then narrowest age band, lowest id on a tie); `SelectMatch` is a pure function with an exhaustive selection test matrix; the M12 handoff note flags catalog-side overlap prevention as future work. |
| Guard chain breaks the assumed-future M02/M21 code | M02/M21 never call `EnterResult`/`MarkReviewed`/`MarkPrinted`/`MarkDelivered` (verified against their inlined surfaces — they touch only draw/registration mutators); the guards are additive on previously-guard-free methods; full-suite gate catches any surprise. |
| Snapshot table growth | 1:1 with resulted rows only; indexed by PK; no mitigation needed at lab scale (noted in ADR). |
| Un-review leaves `ReviewedAtUtc` history-less | Accepted as part of the settled edit-lock policy: columns are overwritten and no history table exists; the T-audit columns + `AuditableEntity` interceptor already capture last-writer (Data Model §10 T-view); no history table is added (out of F5 schema). |
