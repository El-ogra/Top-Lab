## 1. Executive Summary

Module 14 delivers full lifecycle management for the single-table, type-discriminated `ExternalEntity` aggregate (treating doctor / referral-or-contract / partner lab) across Domain, Application, and Infrastructure. At HEAD (`src/TopLab.Domain/ExternalEntities/ExternalEntity.cs`, 89 lines) the entity is **Create-only** with exactly two guards — name required (non-whitespace, trimmed) and *TreatingDoctor must not carry a `PriceListId`* — and no `Update`, delete, ID-regeneration, or Referral-requires-list behaviors. The storage schema already exists in the F5 baseline migration (all columns mapped by `ExternalEntityConfiguration.cs:11-27`, FK `PriceListId → PriceList` with `SetNull`, index on `EntityType`, **no unique index on `GeneratedIdCode`**), so **no migration is needed** — S4 proves zero drift instead of assuming it. The Application layer has no `Features/ExternalEntities/` surface yet (verified: `src/TopLab.Application/Features/` contains `AccessAndNavigation/`, `SamplePipeline/`, `SystemAndPrintSettings/`, `TestCatalogAndReferenceRanges/`, `UsersAndPermissions/` only).

The plan enforces five settled business rules (owner-confirmed OP-1…OP-5, §2): type discrimination via `EntityType` (`TreatingDoctor = 0`, `ReferralOrContract = 1`, `PartnerLab = 2`); doctor-never-has-price-list (FR-M14-002); referral-or-contract-must-have-price-list (FR-M14-003); discrete server-side ID generation into `GeneratedIdCode` for entity identification (FR-M14-005); and the empty-referral sex-based default (`Himself`/`Herself`) as a pure Application-layer read-model resolver, never a stored value (FR-M14-006).

**Slicing:** 5 slices: S1 Domain → S2 reads ∥ S3 writes → S4 Infrastructure proof → S5 close-out. Presentation slices do not exist in this plan because all UI work is out of scope.

## 2. Settled Business Rules (fixed — not open decisions)

These rules are settled facts encoded directly in the slices below. They are not alternatives and must not be reopened:

1. **Empty-referral default.** When a referral-entity name is empty, the default value is produced by a standalone pure resolver returning the frozen literals `"Himself"` (patient sex Male) / `"Herself"` (patient sex Female). It has **no dependency on any system setting**; nothing is stored. Only this sex-based style is implemented — no secondary placeholder style is in scope.
2. **Deletion.** One **uniform guarded hard-delete** rule for all three entity types: deletion is blocked (`Conflict`) while the entity is referenced by a patient (`TreatingDoctorId` or `ReferralEntityId`) or by a sent-out record (`ExternalLabEntityId`); otherwise the row is physically removed. No per-type rules, no soft delete, no `IsActive` column.
3. **Generated-code uniqueness.** Enforced at the Application/handler level **only**: existence pre-check → save → unique-violation catch → bounded retry (max 5 attempts). **No new database unique index and no migration.**
4. **Contact fields & partner-lab price lists.** All contact fields (city, address, phone, fax, responsible-person name/phone) remain optional for every entity type. Partner Lab price-list assignment accepts **any existing price list** — no list-kind restriction (taxonomy belongs to M13).
5. **Assumed settings link rejected.** The assumed link between the empty-referral default and the M22 `SaveTreatingDoctorOnlyFromEntityWindow` flag is unconfirmed and is **not** implemented anywhere in M14; the resulting question is deferred to the future M02 owner via the S5 handoff.

Additional rules derived from code evidence (also settled):

- **Percent range.** `DiscountOrCommissionPercent`, when set, is **0–100 inclusive**, uniform across all three types (column is `decimal(5,2)`; 0–100 is the business-sensible bound).
- **Type transitions.** `Update` re-validates **all** cross-field guards on every call, so a type transition can never bypass guards (TreatingDoctor → no price list; ReferralOrContract → price list required; PartnerLab → price list optional).
- **Generated-code origin.** `GeneratedIdCode` is written **only** by the dedicated ID-generation command (create-then-generate sequencing). No create path accepts a caller-supplied code. Generation is a discrete per-entity action, not an autoincrement.
- **Permission gate.** Every M14 write command carries `IAuthorizedRequest` with `RequiredPermissionCode => "EDIT_SYSTEM_SETTINGS"` (seeded permission Id 10, the established reference-data gate used by M22 and M12). Read queries are open (no `IAuthorizedRequest`), per the established read policy.

### Slice S1 — Domain behaviors and invariants

#### Description

Extend `ExternalEntity` from Create-only to full lifecycle: add `Update` and `RegenerateIdCode` mutators, add the Referral-requires-`PriceListId` guard to `Create` **and** `Update`, add the uniform 0–100 percent guard, normalize optional strings (trim; whitespace → null). |---|---|---|

#### Technical Approach

- Aggregate-root invariants stay inside the entity; no services, no persistence access, no MediatR/EF references in Domain. Existence of `PriceListId` and all reference checks are Application-only.
- `Update(EntityType entityType, string name, string? city, string? address, string? phone, string? fax, string? responsiblePersonName, string? responsiblePersonPhone, PriceListId? priceListId, decimal? discountOrCommissionPercent)` re-validates every cross-field rule: `TreatingDoctor → ReferralOrContract` without a list fails; `ReferralOrContract → TreatingDoctor` while a list is present fails unless the list is cleared in the same call.
- `RegenerateIdCode(string code)`: rejects null/whitespace and length > 50 (matches `nvarchar(50)`); stores the trimmed value. Uniqueness is NOT checkable in Domain — handler responsibility (S3).
- Percent: `null` means not set; otherwise `0 ≤ value ≤ 100` inclusive, uniform across all three types.
- **No delete mutator and no `IsActive` column.** Deletion is `IApplicationDbContext.Remove` after handler-side reference checks, because the checks inherently need the database; a Domain precondition hook would duplicate logic without enforcement power.
- Contact fields stay optional (nullable, matching the configuration); no required-contact guards are invented.

#### Dependencies

None. S1 is the root predecessor of S2 and S3.

#### Technical Approach

- Every write command implements `IAuthorizedRequest` with `RequiredPermissionCode => "EDIT_SYSTEM_SETTINGS"` (seeded Id 10). No new permission code — a seed change would force a migration, and none is sanctioned.
- Layer split: Domain checks null/shape (`PriceListId` presence per type, percent range, name/code shape); handlers check existence (`PriceLists.AnyAsync`) and references. - `Create` does not accept a caller-supplied `GeneratedIdCode`: codes originate only from `GenerateEntityIdCode`, which also serves already-stored rows. Callers needing a code at creation time invoke create-then-generate; recorded in ADR-0030.
- Uniqueness: `GeneratedIdCode` stays `nvarchar(50)` nullable — NULL means not-yet-generated and multiple NULLs are legitimate. Non-null values are guarded by pre-check + catch → `Conflict`; no new index or migration is created for uniqueness (revisit only on observed duplicates — see U3).
- Delete matrix — hard delete only, uniform across types. Handler checks run **before** `Remove`, so behavior is explicit and storage-independent:

- The `SaveTreatingDoctorOnlyFromEntityWindow` flag is neither read nor branched on in any M14 handler: M14 commands ARE the entity-management surface and are always permitted to authorized callers; the deferred flag question is carried in the S5 handoff for the M02 owner.
