## 1. Executive Summary

Module 14 delivers full lifecycle management for the single-table, type-discriminated `ExternalEntity` aggregate (treating doctor / referral-or-contract / partner lab) across Domain, Application, and Infrastructure. At HEAD (`src/TopLab.Domain/ExternalEntities/ExternalEntity.cs:63-88`) the entity is **Create-only** with exactly one guard (TreatingDoctor must not carry a `PriceListId`); there are no `Update`, delete-precondition, or ID-regeneration behaviors. The storage schema already exists in the F5 baseline migration (all columns mapped by `ExternalEntityConfiguration.cs:11-27`, FK `PriceListId → PriceList` with `SetNull`, index on `EntityType`), so **no migration is expected** — S4 proves zero drift instead of assuming it. The Application layer has no `Features/ExternalEntities/` surface yet (verified: `src/TopLab.Application/Features/` contains `AccessAndNavigation/`, `SamplePipeline/`, `SystemAndPrintSettings/`, `TestCatalogAndReferenceRanges/`, `UsersAndPermissions/` only).

The plan enforces the confirmed business rules — type discrimination via `EntityType` (`TreatingDoctor = 0`, `ReferralOrContract = 1`, `PartnerLab = 2` in `src/TopLab.Domain/Common/Enums/EntityType.cs`), doctor-never-has-price-list (FR-M14-002), referral-or-contract-must-have-price-list (FR-M14-003), discrete server-side ID generation into `GeneratedIdCode` (FR-M14-005) — and models the empty-referral sex-based default (`Himself`/`Herself`) as a pure Application-layer read-model resolver, never a stored value (FR-M14-006, second half). The first half of FR-M14-006 (the existing `SystemSettings.SaveTreatingDoctorOnlyFromEntityWindow` flag, M22-delivered) is read-only context for M14, not M14 behavior; the assumed link between that flag and the placeholder is owner-confirmed as unconfirmed and deferred to the future M02 owner (settled OP-1(a) — see Finality Assessment).

**Slicing:** 5 slices following the M-12 precedent (S1 Domain → S2 reads ∥ S3 writes → S4 Infrastructure proof → S5 close-out). Presentation slices do not exist in this plan because all UI work is out of scope.

## 3. Domain Layer (Slice S1)

### Slice S1 — Domain behaviors + tests

#### Description

Extend `ExternalEntity` from Create-only to full lifecycle: add `Update`, add `RegenerateIdCode`, add the Referral-requires-`PriceListId` guard to `Create` and `Update`, add the uniform `0–100` discount guard, normalize optional strings (trim, empty-to-null). Update existing `Create` call sites and tests broken by the new Referral guard inside this slice.

#### Files to Create/Modify

| File | Action | Purpose |
|---|---|---|
| `src/TopLab.Domain/ExternalEntities/ExternalEntity.cs` | Modify | `Update(...)`, `RegenerateIdCode(string)`, Referral-requires-list guard, discount `0–100` guard, normalization; retain doctor-no-list + name-required guards |
| `tests/TopLab.Domain.Tests/ExternalEntities/ExternalEntityTests.cs` | Create | Full guard matrix + happy paths (no such folder exists at HEAD — verified) |

#### Technical Approach

- Aggregate-root invariants stay inside the entity; no services, no persistence access in Domain. Existence of `PriceListId` and all reference checks are Application-only (Auditor I3 — recorded as D13).
- `Update(EntityType entityType, string name, string? city, string? address, string? phone, string? fax, string? responsiblePersonName, string? responsiblePersonPhone, PriceListId? priceListId, decimal? discountOrCommissionPercent)` re-validates every cross-field rule, so a `TreatingDoctor → ReferralOrContract` transition without a list fails, and a `ReferralOrContract → TreatingDoctor` transition retaining a list fails.
- `RegenerateIdCode(string code)`: non-empty after trim, `<= 50` chars; stores trimmed value. Uniqueness is NOT checkable in Domain — documented as handler + storage responsibility (see S3/S4).
- Discount: `null` means not set; otherwise `0 <= value <= 100` inclusive (`decimal(5,2)` storage). Uniform across all three types (owner-confirmed OP-5(a)).
- PartnerLab: no list-kind constraint in Domain; any `PriceListId` shape accepted, existence checked in Application (M13 owns taxonomy).
- No delete-mutator and no `IsActive` column: deletion is `IApplicationDbContext.Remove` after handler-side reference checks (Supervisor ruling D11 — a domain precondition hook would duplicate handler logic that inherently needs the database).
- Contact fields remain optional (nullable, matching `ExternalEntityConfiguration.cs:16-21`); no required-contact guards are invented (Supervisor ruling D12, owner-confirmed OP-5(a)).

#### Dependencies

None. S1 is the root predecessor of S2 and S3.

#### Validation Gate

- `dotnet build src/TopLab.Domain` → 0 errors / 0 warnings.
- All new + existing Domain tests green; every new guard has a negative-path test; type-transition cases covered both directions.
- Coverage: Domain `ExternalEntities` scope ≥ 90% (coverlet, module filter).
- No analyzer suppressions; slopwatch clean on touched files.

#### Risk Level

Medium. `Create` gains a breaking guard by design; missed call sites surface here, not downstream.

#### Technical Approach

- Every write command implements `IAuthorizedRequest` with `RequiredPermissionCode => "EDIT_SYSTEM_SETTINGS"` (M-12 precedent). No new permission code — a seed change would force a migration, and none is sanctioned.
- Layer split (Auditor I3 / D13): Domain checks null/shape (`PriceListId` presence per type, discount range, name shape); handlers check existence (`PriceLists.AnyAsync`) and references. Validators mirror Domain rules textually per the normative table (§7); Domain remains authoritative at runtime (defense in depth).
- `Create` does not accept a caller-supplied `GeneratedIdCode` (validator rejects it when present): codes originate only from `GenerateEntityIdCode`, which also serves already-stored rows. Callers needing a code at creation time invoke create-then-generate; recorded in ADR-0030.
- Uniqueness (owner-confirmed OP-3(a)): `GeneratedIdCode` stays `nvarchar(50)` nullable — NULL means not-yet-generated and multiple NULLs are legitimate. Non-null values are guarded by pre-check + `DbUpdateException` catch → `Conflict`; no new index or migration is created for uniqueness (revisit only on observed duplicates — see U3).
- Delete matrix — hard delete only, uniform across all three types (owner-confirmed OP-2(a)): block with `Conflict` when `Patients.AnyAsync(p => TreatingDoctorId == id || ReferralEntityId == id)` or `SentOutSamples.AnyAsync(s => ExternalLabEntityId == id)`; do NOT block on `CashMovement.RelatedExternalEntityId` (`SetNull`) or on price-list deletion (`SetNull` on `ExternalEntity.PriceListId`). Handler checks run before `Remove`, so behavior is explicit and storage-independent; the `Restrict` catch is a second net, never the primary guard.
- `SaveTreatingDoctorOnlyFromEntityWindow` is neither read nor branched on in any M14 handler: the flag governs patient-entry auto-save (a future M02 concern — deferred question carried in the S5 handoff), while M14 commands ARE the entity-management surface and are always permitted to authorized callers (owner-confirmed OP-1(a)).

Requires S1 (domain API + guards). Parallelizable with S2.

- `dotnet build src/TopLab.Application` → 0 errors / 0 warnings.
