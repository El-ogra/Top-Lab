## 0. How to read this plan

- **Every claim about the current state of the codebase** in §1 was verified by directly reading files at commit `e7ca616` (twice: at the start of work and immediately before writing). No claim relies on documentation prose alone.
- **Slices are the unit of work.** The count is the minimum that reflects the actual remaining work; it is not driven by a target.
- **"Backend only" means Domain + Application + Infrastructure only.** No `View`, `ViewModel`, XAML, dialog, window, navigation-menu wiring, DataTemplate, or other Presentation-layer content is in scope, referenced, or even mentioned except to call out where a Presentation consumer is the natural next step (and is therefore out of scope of this plan).

## 5. Module 1 — Application Access & Main Navigation (backend only)

### 5.1 Honest statement of remaining M01 backend work

M01's Application feature folder at `e7ca616` contains only `CheckDatabaseConnectivityQuery`. The four M01-shaped use cases (sign-in, sign-out, current-session, has-any-absolute-user) live in M17 and are not moved. The remaining M01 Application-layer work is therefore small and **honest about being small**:

- `LockWorkstationCommand` — a thin in-memory `ClearSession` re-export with the `EDIT_SYSTEM_SETTINGS` gate (matching the M17/M22 permission pattern). The natural backend counterpart to a future "lock workstation" UI action (out of scope here; this is the only new M01 Application file).
- The existing `CheckDatabaseConnectivityQuery` is extended to also report the database provider name and the connection string's server (without leaking credentials), so the future login window can show a one-line "Server: <server>, Database: <db>" indicator. This is a DTO change plus a new `IDbConnectionDescriptor` port.

The M01 **Domain** layer has no new entities or mutators (M01's domain grouping is `Users`, already fully delivered in M17). The M01 **Infrastructure** layer adds exactly one new implementation (`SqlServerConnectionDescriptor`) and one DI registration for the new port. M01's Presentation work — login window, status bar wiring, navigation menu wiring for the remaining shell items, the "logout" command consumer, the permission-denial message presentation — is the entire remaining M01 surface and is **explicitly out of scope** for this plan.

The plan reflects this by listing only **two slices** (M01-S1, M01-S2) below. There is no M01-S3, M01-S4, or M01-S5 because there is no read or write surface beyond what M17 already exposes and what M01 adds.

### 5.2 M01 slices

#### M01-S1 — M01 application: extended connectivity DTO and tests

- **Objective.** Add the new `CheckDatabaseConnectivityDto` (with `bool IsConnected`, `string? ServerName`, `string? DatabaseName`) and update the `CheckDatabaseConnectivityQuery` response. Capture the server and database name from a new `IDbConnectionDescriptor` port. Establish the M01 test fake set.
- **Files / classes to add or change.**
  - **Add** `src/TopLab.Application/Features/AccessAndNavigation/Common/ConnectivityDto.cs` — `public sealed record CheckDatabaseConnectivityDto(bool IsConnected, string? ServerName, string? DatabaseName, DateTime CheckedAtUtc);`
  - **Add** `src/TopLab.Application/Features/AccessAndNavigation/Common/Interfaces/IDbConnectionDescriptor.cs` — `public interface IDbConnectionDescriptor { string? ServerName { get; } string? DatabaseName { get; } }` (port for the connectivity DTO to read a redacted connection descriptor without depending on EF Core).
  - **Change** `src/TopLab.Application/Features/AccessAndNavigation/Queries/CheckDatabaseConnectivity/CheckDatabaseConnectivityQuery.cs` — change response type from `IRequest<Result<bool>>` to `IRequest<Result<CheckDatabaseConnectivityDto>>`.
  - **Change** `src/TopLab.Application/Features/AccessAndNavigation/Queries/CheckDatabaseConnectivity/CheckDatabaseConnectivityQueryHandler.cs` — depend on `IDbConnectionDescriptor` and `IDateTimeProvider` in addition to `IApplicationDbContext`; catch `Exception`, return `Result<CheckDatabaseConnectivityDto>.Success(new CheckDatabaseConnectivityDto(false, descriptor.ServerName, descriptor.DatabaseName, _dateTime.UtcNow))` on failure, success on `CanConnectAsync` returning true.
  - **Add** `src/TopLab.Infrastructure/Persistence/SqlServerConnectionDescriptor.cs` — `public sealed class SqlServerConnectionDescriptor : IDbConnectionDescriptor`; parses the `IConfiguration["ConnectionStrings:TopLab"]` value (set during `AddInfrastructure`); returns the `Server=` and `Database=` segments from the SQL Server connection string with the password and any `Password=…;` segment redacted to `Password=***`.
  - **Change** `src/TopLab.Infrastructure/DependencyInjection.cs` — register `IDbConnectionDescriptor` as `Singleton` (depends only on `IConfiguration`, no scoped state). The existing `IWorkstationConnectionSettingsProvider` registration is unchanged.
  - **Add** `tests/TopLab.Application.Tests/Common/Fakes/FakeDbConnectionDescriptor.cs` — a stub descriptor for tests.
  - **Add** `tests/TopLab.Application.Tests/Features/AccessAndNavigation/CheckDatabaseConnectivityQueryHandlerTests.cs` — tests for: connected, not connected, exception path, descriptor surfaces the right server/database, never surfaces the password.
- **Dependencies on prior slices.** None. The slice compiles against the existing `IApplicationDbContext`, the existing `IDateTimeProvider`, and the new `IDbConnectionDescriptor`.
- **Acceptance / completion conditions.**
  - `dotnet build TopLab.sln` reports 0 errors / 0 warnings (full solution), run on the execution machine (§3.1).
  - All new tests green; the existing 529-test baseline is green.
  - The new tests cover: success (returns DTO with `IsConnected=true` and the descriptor's server/database); failure (`CanConnectAsync` returns false → DTO with `IsConnected=false` but the descriptor still populated); exception (DBC throws → DTO with `IsConnected=false`, no exception bubbles); credentials redaction (a connection string with `Password=secret;` results in `ServerName` and `DatabaseName` only — the test asserts the DTO has no `secret` substring anywhere).
  - Diff touches `src/TopLab.Application/Features/AccessAndNavigation/`, `src/TopLab.Infrastructure/`, `tests/TopLab.Application.Tests/`, and the DI registration only. No Presentation. No other Domain. No M17/M22/M12/M14 files.

#### M01-S2 — M01 application: `LockWorkstationCommand` and tests

- **Objective.** Add the `LockWorkstationCommand` — a thin in-memory command that clears the current session and gates on `EDIT_SYSTEM_SETTINGS` (matching the M17/M22 permission pattern, the same gate that all of M22's writes use — see `EDIT_SYSTEM_SETTINGS` row id 10 in `PermissionConfiguration.cs`). This is the only M01-owned write surface. No new Domain mutator is needed (the in-memory state lives in `CurrentUserService`, which already has `ClearSession()`).
- **Files / classes to add or change.**
  - **Add** `src/TopLab.Application/Features/AccessAndNavigation/Commands/LockWorkstation/LockWorkstationCommand.cs` — `public sealed record LockWorkstationCommand : IRequest<Result>, IAuthorizedRequest { public string RequiredPermissionCode => "EDIT_SYSTEM_SETTINGS"; }`
  - **Add** `src/TopLab.Application/Features/AccessAndNavigation/Commands/LockWorkstation/LockWorkstationCommandHandler.cs` — depends on `ICurrentUserService`; calls `_currentUser.ClearSession()`; returns `Result.Success()`.
  - **Add** `src/TopLab.Application/Features/AccessAndNavigation/Common/AccessAndNavigationAccessPolicy.cs` — constants for the permission codes M01 depends on (`public const string EditSystemSettings = "EDIT_SYSTEM_SETTINGS";`). Mirrors the implicit "magic string" pattern that M12/M14/M22 use.
  - **Add** `tests/TopLab.Application.Tests/Features/AccessAndNavigation/LockWorkstationCommandHandlerTests.cs` — tests for: handler calls `ClearSession` exactly once; handler does not touch `IApplicationDbContext`; handler does not throw on already-cleared session; handler returns `Result.Success()`.
  - **Add** `tests/TopLab.Application.Tests/Features/AccessAndNavigation/AccessAndNavigationAuthorizationTests.cs` — analogue of `ExternalEntitiesAuthorizationTests.cs`; asserts `LockWorkstationCommand.RequiredPermissionCode == "EDIT_SYSTEM_SETTINGS"` and that `AuthorizationBehavior` returns the standard denial message ("أنت لا تملك الصلاحية لهذا العمل راجع مدير النظام") when the user lacks the permission.
- **Dependencies on prior slices.** M01-S1 (for the established M01 folder shape and test fakes).
- **Acceptance / completion conditions.**
  - `dotnet build TopLab.sln` 0/0.
  - All new tests green; 529-baseline green; M01-S1 tests green.
  - The handler is purely in-memory (no `IApplicationDbContext` injection) — verified by test inspection.
  - Authorization test: a user with `IsAbsolutePermission = true` bypasses the gate; a user with the `EDIT_SYSTEM_SETTINGS` grant passes; a user with neither gets the standard denial.
  - Diff is local to M01's feature folder + test project + (no DI change — `ICurrentUserService` is already registered).
