## 0.1 Changelog (what changed and why)

1. **Item-mutation mechanics corrected (the most material change).** The original D3 option (a) assumed handlers would "load the aggregate including items" through the collection navigation. Re-verification shows this is **not possible with the current port**: `IApplicationDbContext` exposes only `Set<T>()`, `Add`, `Update`, `Remove`, `SaveChangesAsync`, `CanConnectAsync` — there is **no `Include`/eager-loading capability** anywhere in the Application layer (verified by reading the interface in full and grepping all handlers). The established M12 precedent (`SaveWorkGroupLogItemsCommandHandler`, read in full) works around this by existence-checking flat rows via `Set<WorkGroupLogItem>()` and persisting rows explicitly with `_db.Add/Remove`, while the aggregate methods mutate the in-memory `_items`. The plan specifies the safe form of that pattern per command (§3, M13-S3) and explicitly flags a **double-tracking hazard** in the naive version of it (see §7 risk table). D3 is re-worded accordingly (§9).
2. **`RemoveItem`-on-absent semantics changed from no-op to throw.** The original draft froze "no-op, matching `PaymentOperation.Void()`". Verified: `PaymentOperation.Void()` is not a removal guard at all (it merely sets a flag), whereas the actual removal precedent — `WorkGroupLog.RemoveItem` — **throws `ArgumentException` ("Test is not in the work group log.", nameof(testId)) when the item is absent**. The plan aligns `PriceList.RemoveItem` / `CustomGroup.RemoveItem` to the verified precedent; handlers translate the absence case to `Error.NotFound` before calling the domain method.
3. **`ValidatorRegistrationTests` location corrected.** The file is `tests/TopLab.Infrastructure.Tests/Persistence/ValidatorRegistrationTests.cs` (verified) — the original draft addressed it under `tests/TopLab.Application.Tests/DependencyInjection/`, a path that does not exist. The extend-targets in M13-S4 are corrected.
4. **"No test deletion exists" nuance.** Verified: there is **no `DeleteTest` command** at this commit (M12 ships Deactivate/Reactivate only). The orphan-risk framing is reworded: the `PatientTest → Test` Restrict FK is real (snapshot verified), but since tests are never hard-deleted today, orphan `PriceListItem`/`CustomGroupItem` rows can only arise if a future module introduces test hard-delete without application guards. The negative FK-matrix assertions are kept so any such schema change is caught.
5. **Reference citations re-verified verbatim.** All §1.4 rows were re-read from freshly extracted `RLS_Learn.pdf` text; the "Lab to Lab usable as a price list for labs" detail and the "multiple comments per test" detail are quoted from the text.
6. **Normative message table extended** with the detach-missing and item-not-in-group messages that earlier slices referenced but did not freeze. M13 only consumes the item-not-in-list and item-not-in-group messages (the detach-missing message is not relevant to M13's commands and is not in M13's table).
7. Minor: test-project layout verified (`tests/TopLab.Domain.Tests`, `tests/TopLab.Application.Tests`, `tests/TopLab.Infrastructure.Tests`).

## 2. Settled Business Rules (fixed — not open decisions)

Derived from verified code + reference text; encoded directly in the slices:

1. **No new migration.** All tables/columns/FKs needed by M13 already exist from the F5 baseline (§1.3, line-level verified); a model-vs-snapshot zero-drift gate runs in the Infrastructure slice and any discovered drift (there should be none) triggers plan revision, not silent migration.
2. **Permission gate.** All M13 write commands carry `IAuthorizedRequest` with `RequiredPermissionCode => "EDIT_SYSTEM_SETTINGS"`; all read queries are open (M12/M14 precedent, verified).
3. **Result pattern.** No exceptions cross the Application boundary for expected failures; domain `ArgumentException`s are translated to Arabic `Error.Validation` via a feature-local `DomainFailureTranslator` (M14 precedent, read in full); expected lookup misses → `Error.NotFound`; reference-blocked deletes → `Error.Conflict`; duplicate-reference races at save time → the `IsReferenceConflict(ex)` catch (M14 `DeleteExternalEntityCommandHandler` precedent) mapped to `Error.Conflict`.
4. **Money validation.** Prices (`PriceListItem.Price`, `CustomGroupItem.Price`) must be `>= 0`; zero is allowed (consistent with the verified `Test` guard `PatientPrice must be >= 0`). Domain guards added at the item constructors and at the price-update methods; validators mirror with `GreaterThanOrEqualTo(0)`.
5. **Name/text rules.** `PriceList.Name`, `CustomGroup.Name`: required, trimmed, max 150 (column length, verified). `TestComment.CommentText`: required, trimmed, max 1000 (column length, verified) — the length guard is added to the domain entity (today it exists only in the EF configuration), exposed as `TestComment.MaxCommentTextLength = 1000` following the `ReferenceRange.MaxCommentLength` / `Test.MaxTestCodeLength` constant precedent (verified).
6. **Referential integrity at the Application layer.** Handlers existence-check `TestId` targets (M12 catalog, active or not — the reference adds any catalog test to lists/groups; deactivation semantics for list membership is a downstream consumption concern), `PriceListId`, `CustomGroupId` before item operations; duplicate item (same composite key) → `Error.Conflict` (price updates go through the upsert-style `SetItemPrice` — see slice M13-S3 for the exact split between "set price" and "add item" semantics).
7. **Price-list delete guard.** Deleting a price list is **blocked (`Conflict`) while any `ExternalEntity.PriceListId` references it** (the reference system deletes lists freely, but silently nulling a live contract entity's price list — which is what the DB-level `SetNull` would do — would manufacture domain-invalid `ReferralOrContract` entities, violating the verified `ValidatePriceListRule` invariant, and silently reprice future patients at walk-in prices; blocking is reversible by reassignment). Items cascade with the list at the DB level (FK Cascade, verified). **Confirmed rule (D1-a, owner-approved):** the block described here is the implemented behavior.
8. **Test-comment and custom-group delete.** Hard delete; comments cascade with their `Test` (FK Cascade, verified); custom-group items cascade with their group (FK Cascade, verified). No patient-side reference to either exists at this commit (verified — grep over `Patient`/`PatientTest` finds no `CustomGroup`/`TestComment` reference), so no delete guard is needed beyond existence.
9. **Read surface completeness.** For each of the three managed concepts (price lists, comments, custom groups): list query + detail query, with the reference-shown shapes — price-list detail includes its items with test names and prices; custom-group detail includes its items with test names and prices; test-comment listing is per-test (the reference inserts comments by test via a per-test dropdown).

### Slice M13-S3 — Application write surface + validators (Application layer)

**Objective.** Commands for the full maintenance workflow shown in the reference: create/rename/delete price list, add/edit/remove priced items; add/update/delete fixed comments; create/rename/delete custom group, add/edit/remove priced items.

**Item-mutation mechanics (mandatory pattern — the V2 correction).** The Application port has no `Include`, so EF cannot be asked to populate `_items` through the port; the verified M12 precedent (`SaveWorkGroupLogItemsCommandHandler`) therefore persists item rows explicitly. Every item-mutating handler in this slice follows this exact protocol:

1. Load the header: `var list = _db.Set<PriceList>().FirstOrDefault(l => l.Id.Value == request.Id)` (tracked by the real context; returned as-is by the fake).
2. Existence-check the `TestId` target via `Set<Test>()`.
3. **Pre-check the item row against the flat set**: `var row = _db.Set<PriceListItem>().FirstOrDefault(i => i.PriceListId.Value == request.PriceListId && i.TestId.Value == request.TestId)`.
4. Call the aggregate method that matches the intended outcome (`SetItemPrice` for upsert, `RemoveItem` for removal) **inside try/catch (ArgumentException) → translator**, so domain invariants are enforced even if the pre-check and the in-memory collection disagree.
5. Persist the outcome against the flat set **idempotently**:
   - Upsert: `if (row is null) _db.Add(new PriceListItem(list.Id, TestId.Create(request.TestId), request.Price)); else _db.Update(row with new price)` — concretely: mutate via the tracked row's `UpdatePrice` is internal, so the handler uses `row` from the set and calls `_db.Update(row)` after applying the new price through the aggregate-returned/tracked instance (see note below); if absent, `_db.Add(...)`.
   - Removal: `if (row is not null) _db.Remove(row);` (idempotent even when the aggregate threw first — the translator return already happened, so this branch is only reached on the happy path).
6. `await _db.SaveChangesAsync(ct)`.

**⚠ Double-tracking hazard (must be respected in every item handler).** Do **not** `_db.Add(...)` an instance taken from `list.Items` (the collection the aggregate just mutated) while *also* adding a separately constructed row — the real `DbContext` would then track two `PriceListItem` instances with the same composite key and throw at `SaveChanges`. The verified M12 handler avoided this by adding a **freshly constructed** row and never touching the aggregate's instances — but it leaves the aggregate's in-memory `_items` populated with untracked instances, which is harmless only because the aggregate instance is discarded after the command. The safest form (and the one this plan mandates) is: **treat the aggregate method as the invariant-checker and the flat set as the persistence surface** — i.e. perform step 4 for invariant enforcement, then perform step 5 purely against `Set<PriceListItem>()` rows (fresh instance for Add; tracked row from step 3 for Update/Remove). Tests in the fake context and one EF Core InMemory integration test (M13-S4) both pin this behavior. **This aggregate-as-invariant-checker + flat-set-persistence form is the confirmed approach (D3-a, owner-approved); the flat-row-only alternative is rejected and is not part of this plan.**
