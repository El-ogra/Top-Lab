### 4.1 F-03 — the only production logger writes through a call the Release compiler deletes

**Evidence (VERIFIED-BY-CODE-INSPECTION):**

```

src/TopLab.Presentation/DependencyInjection.cs:115  internal sealed class WpfAppLogger : IAppLogger

`grep -rn "Debug.WriteLine" src/ --include=*.cs` returns exactly that one line. `Debug.WriteLine` carries `[Conditional("DEBUG")]`, so the C# compiler removes the call *and its argument expression* outside `DEBUG`.

**Consumers of `IAppLogger` (exhaustive, VERIFIED-BY-EXECUTION):** `LoggingBehavior.cs:17,19,41,47` and `DailyBackupHostedService.cs:18,24,65,76,83`; the only other implementation is a test fake. `src/TopLab.Infrastructure/DependencyInjection.cs` contains **no** `IAppLogger` registration.

**Log-location convention already established in this repository (no new setting needed):** `%ProgramData%\TopLab\` is the documented workstation-local root used by `App.xaml.cs:32-34`, `ConfigurationFileService.cs:9-10`, `JsonPhoneBookStore.cs:24`, `JsonPurchasesListStore.cs:23`, `JsonLabPrintTextStore.cs:19`, and `ILabPrintTextStore.cs:16` states the same path in its contract. **Privacy constraint (verified):** `IAppLogger.Log(string requestName, string outcome, TimeSpan duration)` receives only a *type name* and an *outcome token*. `LoggingBehavior.cs:37-39` builds the outcome as `"Success"`, `$"Failure:{result.Error?.Type}"` or `$"Exception:{ex.GetType().Name}"` (`:47`) — never a payload, a password, a patient identifier or a result value. `DailyBackupHostedService` passes literals and, at `:83`, `$"backup error: {ex.Message}"` (a backup file/directory path). **The fix must therefore keep the interface signature unchanged** — that is what makes payload logging structurally impossible. **Search for a compensating control (VERIFIED-BY-EXECUTION):** `grep -rn "ICurrentUserService|IsAbsolutePermission|HasPermission|IsAuthenticated" src/TopLab.Application/Features/UsersAndPermissions/ --include=*.cs` shows that **none of the six writable handlers** (`CreateUser`, `UpdateUser`, `DeleteUser`, `DeactivateUser`, `ReactivateUser`, `SaveUserPermissions`) nor `GetUsersQueryHandler` / `GetUserByIdQueryHandler` injects `ICurrentUserService`. Every `IsAbsolutePermission` occurrence in the feature is either a read of the **target** `User` row, or the `SetAbsolutePermission` write, or DTO projection.

There *is* a partial UI control, and it does not cover this path: `UserManagementViewModel.cs:252-274` (`UpdateAuditAccessVisibility`) blocks granting `PT_AUDIT_ACCESS` to a non-absolute user (`audit.IsEnabled = IsAbsolutePermission;` at `:268`, `audit.IsGranted = false;` at `:271`). It says nothing about `IsAbsolutePermission`.

The "last absolute administrator" floors in `UpdateUserCommandHandler.cs:32-40`, `DeleteUserCommandHandler.cs:33-40` and `DeactivateUserCommandHandler.cs:30-37` are **target-only** — they protect the *target* from losing the flag, not the *actor* from gaining it.

**Design (the no-new-permission-code fix, §9.4).** Because `IAuthorizedRequest` attaches one code to a request *type* and knows nothing about the actor, any access-policy solution would need a code and would drag `SignInCommand` — the session-creating request — into the gate. The coherent fix is therefore entirely inside the handlers, plus one defensive UI binding:

1. **Anti-escalation:** in `CreateUserCommandHandler` and `UpdateUserCommandHandler`, reject with `Error.Forbidden` when the request asks for `IsAbsolutePermission == true` and the actor is not itself absolute (or is not authenticated) — before any `SaveChangesAsync`.
2. **Actor floor:** in `UpdateUserCommandHandler`, `DeleteUserCommandHandler` and `DeactivateUserCommandHandler`, stop a non-absolute actor from *demoting*, *deleting* or *deactivating* an absolute target.
3. **Session enforcement:** `!_currentUser.IsAuthenticated → Error.Forbidden` in `CreateUser`, `UpdateUser`, `DeleteUser`, `DeactivateUser`, `ReactivateUser`, `SaveUserPermissions`, `GetUsers`, `GetUserById` — on the literal pattern already used at `ChangeOwnPasswordCommandHandler.cs:26`.
4. **UI depth-defence:** bind `IsEnabled` on the absolute-permission checkbox to a `UserManagementViewModel` property derived from the current user's absolute flag.

**The four requests that must stay reachable without a normal permission gate (confirmed against the code):** `SignInCommand` creates the session (`SignInCommandHandler.cs:56` is the only `SetSession` call in the feature); `SignOutCommand` and `GetCurrentSessionQuery` operate on the live session; `VerifySecondaryPasswordQuery` is the re-challenge behind the «المستخدمون» and «الحسابات» navigation. The fix adds **no** `IAuthorizedRequest` to any of them, and the three new handler guards are placed only in the eight components listed above, none of which is on the login path. `HasAnyAbsoluteUserQuery` is the first-run admin gate at `App.xaml.cs:73-90` and is likewise untouched.

**Both upstream behaviors short-circuit** (VERIFIED-BY-CODE-INSPECTION): `ValidationBehavior.cs:47` returns `BuildFailure(...)` without calling `next()`; `AuthorizationBehavior.cs:39` returns `BuildForbidden(...)` without calling `next()`.

```
REPO/INVALID   -> IsSuccess=False ErrType=Validation handlerCalls=0 logEntries=0
REPO/FORBIDDEN -> IsSuccess=False ErrType=Forbidden  handlerCalls=0 logEntries=0
REPO/ALLOWED   -> IsSuccess=True  ErrType=           handlerCalls=1 logEntries=1 entries=[ProbeRequest|Success]

LOG1/INVALID   -> IsSuccess=False ErrType=Validation handlerCalls=0 logEntries=1 entries=[ProbeRequest|Failure:Validation]
LOG1/FORBIDDEN -> IsSuccess=False ErrType=Forbidden  handlerCalls=0 logEntries=1 entries=[ProbeRequest|Failure:Forbidden]

`REPO/*` is the repository's current order (Validation, Authorization, Logging); `LOG1/*` is the same three behaviors with `LoggingBehavior` registered first.

1. In MediatR 12.5.0 **the first registered behavior is the outermost wrapper**. Registering Logging last makes it the innermost — adjacent to the handler.
2. With the repository's order, a validation-rejected request produces **0** log entries and an authorization-denied request produces **0** log entries. With Logging first, both produce exactly one, with the outcome correctly attributed (`Failure:Validation`, `Failure:Forbidden`).
3. Therefore, today, **every rejected and every invalid request in the application is invisible to the log.** This is the defect.

**Privacy re-check, required before making the change:** the probe output shows the logged content is `typeof(TRequest).Name` plus a categorical outcome token only. `LoggingBehavior.cs:29` computes `requestName` from the *type*, never from the instance; `:37-39` and `:47` build the outcome from `ErrorType` / exception *type* only. **No request payload, no password, no patient identifier and no result value passes to `IAppLogger`.** Wrapping authorization and validation therefore cannot introduce sensitive data into the log, and no signature change is required.
