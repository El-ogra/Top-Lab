## 1. Execution Philosophy (repo-native loop-engineering)

This programme follows the repository's established loop-engineering methodology exactly as demonstrated in `Docs/OpenCode/Execution-Prompts.md`, `S-00.md`, `S-01.md`, `S-02.md` and the `M-xx`/`M-xx-memory.md` pairs:

- **Two-artifact shape:** this plan (`S-03.md`) + the loop memory (`S-03-memory.md`). The memory file is the persistent execution state; the plan is the requirements surface.
- **10-stage cycle per slice:** (1) Pre-Execution Verification → (2) Deep Understanding → (3) File Analysis → (4) Planning → (5) Execution → (6) Post-Execution Verification → (7) Validation Gate → (8) Documentation Update → (9) Memory Status Update → (10) Git Commit (local only).
- **Quality gate (non-negotiable):** a slice is complete ONLY when (a) its implementation is fully complete per this plan + the P2 plan, (b) the ENTIRE solution builds with zero errors AND zero warnings (`dotnet build TopLab.sln`), (c) ALL existing automated tests pass (`dotnet test TopLab.sln` — full suite, not just affected tests), (d) the slice's own Validation Gate passes with concrete evidence.
- **Evidence over claims:** "implemented" is never evidence. Evidence = build output, test output, grep/diff gates, file inspection, and (for UI, where no UI test harness exists in the repo) an explicit manual-verification checklist with its result recorded — never invented.
- **Stop rule:** the SAME failure (a specific build error, file-edit failure, or test failure) occurring **5 CONSECUTIVE** times → STOP entirely and write a Stop Report in the memory file. Ordinary expected test failures resolved within the same correction cycle do not count.
- **Git policy:** automatic LOCAL commit after each verified slice on the CURRENT branch (`main`); NEVER create a branch, NEVER push, NEVER rewrite history. Commit format: `[S-03] Slice N/8: <slice title> — loop-engineering`.
- **No half-wired states (binding, per S-01/S-02 precedent):** every enabled control ships with a complete backend path; anything whose backend cannot exist yet ships disabled, matching the existing `NavigationItem.IsEnabled` placeholder idiom.
- **Preserve existing behaviour:** no change unless the P2 plan explicitly requires it. No broad rewrites, no unrelated cleanup, no speculative abstractions, no future-proofing.
- **No EF migration anywhere in P2** (zero-drift gate on every slice; any discovered need is a STOP-and-report, never a silent migration).
- **The P2 plan is authoritative for requirements.** This document assigns scope/order/gates; for field lists, validation messages, state behaviour and screen specs it cites the P2 plan section (e.g. "P2 M02 §4 S-M02-3"). Verbatim Arabic messages quoted in the P2 plan are binding. Where the P2 plan tags an item **Inference / Uncertain / يتطلب إنشاء / بانتظار قرار المالك**, that tag is carried into execution: verify-before-build for Inference/Uncertain; build for «يتطلب إنشاء»; never silently decide an owner-pending item.

## 3. Dependency Overview & Slice Order

All backends consumed by P2 already exist at the pinned commit (every Command/Query/DTO is Confirmed). P2 is Presentation-layer composition work plus **zero new backend artifacts** — unlike S-02 (which shipped the D7 command), nothing in P2 authorises a new Application-layer type unless an owner decision converts a tagged gap into one (in which case: STOP-and-report first).

Dependency edges that determine slice order:

1. **Editor state surfacing (Slice 0)** is the foundation: `IsBusy` indicator, empty-state and error-state idioms created here are reused by every later slice (search results, history, account screen, worksheets).
2. **Search-to-edit (Slice 1)** and **visit history (Slice 2)** both extend `PatientEditorView`; sequenced after Slice 0 so they inherit its state idioms; search first because it is the P2 plan's primary new entry path into edit mode (`LoadPatientAsync`), which the history section then assumes.
3. **Editor action wiring (Slice 3)** binds the three orphaned M02 commands (`AddProfileToVisit`/`AddCustomGroupToVisit`/`ClearAllTests`) inside the editor; placed after the editor's structural additions so the action bar is stable.
4. **Patient account screen (Slice 4)** is entered from the editor's totals row (P2 M03 §4: «جعل صف المجاميع قابلاً للنقر») — cannot precede the editor slices; it reuses `RecordPayment`/`Settle`/`PrintReceipt`/`PrintInvoice` already wired in the editor.
5. **Billing dialogs (Slice 5)** open from the account screen's toolbar/rows — after Slice 4.
6. **Invoice preview (Slice 6)** lives in the account screen and consumes the dialogs' refresh idiom — after Slice 4/5.
7. **WorkSheets screen (Slice 7)** is independent of M02/M03 code but reuses the S-02 wiring recipe (shell branch + `DataTemplate` + DI) and the Slice-0 state idioms; placed last because it settles a shell navigation debt and is the largest single new view.
