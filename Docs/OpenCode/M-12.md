# Module 12 — Test Catalog & Reference Ranges: Execution Plan

## Plan Status

This is the final, complete execution plan for Module 12. Zero open points remain.

All decisions have been resolved by confirmed owner decisions or sound architectural judgment applied consistently with the module's conventions:

1. **PatientTitle scope** — deferred out of M-12. Confirmed final. No PatientTitle command, query, DTO, or domain change ships in M-12.
2. **Test and TestGroup lifecycle** — Active/Inactive lifecycle with no hard delete for either entity. Confirmed final. M-12 implements `Deactivate`/`Reactivate` commands for both entities, and the `IsActive` boolean field on both the `Tests` and `TestGroups` tables.
3. **TestGroup deactivation cascades to member Tests** — confirmed binding. Deactivating a TestGroup atomically deactivates every Test currently assigned to that TestGroup within the same transaction. This ensures a group and its contents are retired from active use together, preventing orphaned active tests under an inactive group.
4. **TestGroup reactivation does NOT cascade to member Tests** — resolved by architectural judgment. When a TestGroup is reactivated, each member Test retains its current `IsActive` state. Tests must be individually reactivated if desired. Rationale: a Test may have been deactivated independently of the group (e.g., the test itself was deprecated, pending review, or temporarily unavailable from a supplier); cascading reactivation could reactivate tests the owner intentionally kept inactive for clinical or business reasons. The asymmetry — deactivation cascades down for safety and consistency; reactivation requires explicit per-test action — is the standard lifecycle-management pattern and the safe default.

## 1. Executive Summary

Module 12 delivers the Test Catalog and Reference Ranges management surface. It introduces three new schema columns — `Tests.TestCode` (`nvarchar(50) NOT NULL`, unique), `Tests.IsActive` (`bit NOT NULL`, default `true`), and `TestGroups.IsActive` (`bit NOT NULL`, default `true`) — delivered in exactly one EF migration. All other M-12 tables already exist in the F5 baseline. The plan touches Domain, Application, and Infrastructure layers only. Presentation/UI work is explicitly out of scope and will be delivered separately.

**Settled decisions (binding, override any conflicting prior planning):**
- `TestComment` is entirely deferred to M-13. M-12 contains zero TestComment changes (no `Update` method, no CRUD, no references in commands or queries).
- `PatientTitle` is deferred from M-12. No PatientTitle command, query, DTO, or domain change ships in M-12.
- "Test number" (FR-M12-001) is resolved as a new user-facing **`Tests.TestCode`** column, `nvarchar(50)`, required, unique, trimmed. It is NOT a reuse of the internal `TestId` primary key.

TestGroup deactivation cascades atomically to all member Tests; reactivation does NOT cascade (each Test must be individually reactivated).

**Search filter (FR-M12-001):**

`SearchTestCatalogQuery(string? SearchTerm, int? TestGroupId, bool IncludeInactive = false)` filters on:

1. **Active-filter (default):** `WHERE t.IsActive = true` unless `IncludeInactive` is `true`.
2. Text axes: `Test.Name.Contains(term)` OR `Test.ReportName.Contains(term)` OR `Test.Barcode.Contains(term)`
3. `TestGroup.Name.Contains(term)` via the `TestGroupId` navigation — containing-group axis (only active groups by default unless `IncludeInactive`)
4. `Test.TestCode.Equals(term)` (exact match — codes are unique; case-insensitive by SQL Server default collation)

Filters combine with `OR` (any text match wins). An optional `TestGroupId` exact-match filter is applied additionally. SQL Server default collation is `SQL_Latin1_General_CP1_CI_AS` (case-insensitive, accent-insensitive); plain `Contains` suffices — no `EF.Functions.Like` or `.ToLower()` needed.

Empty `SearchTerm` (null/whitespace) → all tests (subject to the `TestGroupId` and `IsActive` filters if provided).

**Read-side behavior for inactive records:**
- **Default search/selection (for new operations):** `SearchTestCatalogQuery` with `IncludeInactive = false` (default) returns only `IsActive == true` tests and groups. This is the query used by the Presentation layer's catalog screen and any new-operation lookup.
- **Historical/reporting visibility:** `SearchTestCatalogQuery` with `IncludeInactive = true` returns all tests regardless of active status. The Presentation layer uses this for reporting views, audit screens, and historical result lookups.
- **GetTestByIdQuery:** returns any test by ID regardless of active status (the caller needs to see the full record, including its `IsActive` flag).
- **GetTestGroupsQuery:** accepts optional `bool IncludeInactive = false` parameter. When `false`, only active groups are returned.

**Queries are not `IAuthorizedRequest`** — the read surface is open, mirroring `GetUsersQuery` and `GetSystemSettingsQuery` precedent. The sensitive entry point is gated at the Presentation layer (out of M-12 scope).

**Handler dependencies:** `IApplicationDbContext` only.

### 5.3 ADR-0028 Content

- **Title:** Add user-facing `Tests.TestCode` column for FR-M12-001 "test number" search.
- **Context:** FR-M12-001 requires searchable by test name, containing group, or test number. "Test number" is a user-entered, display-facing, stable identifier distinct from the internal `TestId` surrogate. No existing column satisfies this; reusing `TestId` is rejected because it is internal and not display-stable across data imports.
- **Decision:** Add `Tests.TestCode nvarchar(50) NOT NULL` with a unique index `IX_Tests_TestCode` using the database default collation (`SQL_Latin1_General_CP1_CI_AS`, case-insensitive — same precedent as `IX_Users_UserName`). Domain enforces required + trimmed; Application validator enforces max-length 50; DB enforces uniqueness.
- **Consequences:** One new EF migration; the F5 baseline tables are otherwise unchanged; search by `TestCode` is exact-match (codes are unique); M-04 (or any downstream module) may display `TestCode` on receipts and reports. M-12 does not change `PatientTest` or any other downstream schema.

### 5.4 ADR-0029 Content

- **Title:** Add `IsActive` lifecycle field to `Tests` and `TestGroups` with Deactivate/Reactivate write surface and cascading deactivation.
- **Context:** The module requires a way to retire tests and test groups from active use without destroying historical data. Hard delete is rejected because it would orphan reference ranges, work-group log items, and future patient-test rows. A boolean lifecycle flag is the simplest mechanism that satisfies this need.
- **Decision:** Add `Tests.IsActive bit NOT NULL DEFAULT 1` and `TestGroups.IsActive bit NOT NULL DEFAULT 1`. The write surface exposes `DeactivateTest`/`ReactivateTest` and `DeactivateTestGroup`/`ReactivateTestGroup` commands. No hard delete of Test or TestGroup exists in M-12. **Deactivating a TestGroup cascades atomically to all member Tests** — the handler loads every Test with `TestGroupId == group.Id` and sets `IsActive = false` on each, within a single `SaveChangesAsync` call (single transaction). **Reactivating a TestGroup does NOT cascade** — member Tests retain their current `IsActive` state and must be individually reactivated if desired. This asymmetry is deliberate: deactivation cascading ensures a group and its contents are retired together (no orphaned active tests under an inactive group); non-cascading reactivation prevents inadvertently reactivating tests that were individually deprecated, pending review, or temporarily unavailable. Read-side queries filter by `IsActive = true` by default; an `IncludeInactive` parameter explicitly overrides this.
- **Consequences:** The migration adds two columns with a `DEFAULT 1` constraint (existing rows become active). The `DeactivateTestGroupCommandHandler` must query `_db.Set<Test>().Where(t => t.TestGroupId == groupId && t.IsActive)` to find affected tests, then call `Deactivate()` on each and add/update them. The read surface must pass `IncludeInactive` correctly. The Presentation layer (future) uses the flag to grey-out or hide inactive records in catalog and group lists. Reactivation is always possible per-test.

### 5.5 Migration Scope Gate

The migration must touch **only** the `Tests` and `TestGroups` tables:
- `Tests`: `AddColumn("TestCode", nvarchar(50), nullable: false)`, `AddColumn("IsActive", bit, nullable: false, defaultValue: true)`, `CreateIndex` unique on `TestCode`.
- `TestGroups`: `AddColumn("IsActive", bit, nullable: false, defaultValue: true)`.

A reviewer gate confirms no other change.
