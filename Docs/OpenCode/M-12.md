## Cross-Review Changelog

This file was updated after a cross-review with `Docs/Hermes/M-12.md`. The following items are concrete improvements adopted from that review, applied minimally and within this plan's own structure:

- **CR-1 (from Hermes §S1):** Added `ReferenceRangeSnapshot` value object to S1 to handle the freeze contract (BR-05/FR-M12-006). This is a Domain-driven design approach that ensures historical patient results retain their original reference-range values.
- **CR-2 (from Hermes §S1):** Added domain events (`TestChangedEvent`) for each Test mutator to enable finer audit granularity.
- **CR-3 (from Hermes §S8):** Added comprehensive Arabic error-message table to S8 for all M-12 operations.
- **CR-4 (from Hermes §S3):** Improved ID-generation strategy: replaced `Max()+1` pattern with `TestId.Create(0)`. **Rationale:** (1) avoids the `Max()+1` race condition where concurrent inserts could compute the same next ID, (2) follows the standard EF Core pattern for value-generated-on-add properties, (3) the actual ID is database-generated via IDENTITY and read back by EF Core after `SaveChangesAsync()`. **Note:** Both patterns (`Max()+1` and `Create(0)`) may work on SQL Server; the `Create(0)` choice is based on cleanliness and race-condition avoidance, not on proven failure of `Max()+1`. An integration test is recommended to confirm runtime behavior.

**Items NOT adopted (genuine divergence with Hermes):**
- Hermes uses per-field typed mutators (Rename, SetReportName, etc.); this plan keeps the single bulk `Update` method. Both are defensible; the bulk approach is simpler and matches the existing codebase pattern. This is treated as an **open decision** (Q2 below).
- Hermes includes PatientTitle in M-12 scope; this plan omits it. This is treated as an **open decision** (Q1 below).

## Executive Summary

Module M-12 delivers the Test Catalog management screen and Reference Range configuration for the TopLab laboratory information system. This module touches all four Clean Architecture layers and involves six domain entities (`Test`, `TestGroup`, `ReferenceRange`, `TestComment`, `WorkGroupLog`, `WorkGroupLogItem`). The existing domain entities already have `Create` factory methods and some have `Update`; this plan fills the behavioral gaps, builds the full Application query/command surface, and delivers the WPF Presentation layer.

## Slice S1 — Domain Behaviors (Mutators + Invariant Guards)

> **Freeze Contract (BR-05/FR-M12-006):** When a result is entered, the reference-range values active at that moment must be preserved independently of any later changes to the `ReferenceRange` table. The `ReferenceRangeSnapshot` value object captures this frozen state. The actual persistence of this snapshot on `Result` rows is M-04's responsibility (per ambiguity #5); M-12 only defines the Domain shape.

```csharp
public sealed record GetTestCatalogQuery(
    string? SearchTerm = null,
    int? TestGroupId = null) : IRequest<Result<IReadOnlyList<TestSummaryDto>>>;
```

Handler filters by `SearchTerm` against `Name`, `ReportName`, `Barcode`, and `Test Number` (Contains, case-insensitive), and by `TestGroupId` if provided. **Test number search:** attempt `int.TryParse(SearchTerm)` — if successful, include tests where `t.Id.Value == parsedInt` in the filter (OR logic with text matches). Uses `_db.Set<Test>()` with `.Include`-free projection (join via TestGroupId). Returns `Result<IReadOnlyList<TestSummaryDto>>`.

```csharp
// Pseudo-code for search filter:
var query = _db.Set<Test>().AsQueryable();

if (!string.IsNullOrWhiteSpace(request.SearchTerm))
{
    if (int.TryParse(request.SearchTerm, out int testNumber))
    {
        query = query.Where(t =>
            t.Name.Contains(request.SearchTerm) ||
            t.ReportName.Contains(request.SearchTerm) ||
            (t.Barcode != null && t.Barcode.Contains(request.SearchTerm)) ||
            t.Id.Value == testNumber);
    }
    else
    {
        query = query.Where(t =>
            t.Name.Contains(request.SearchTerm) ||
            t.ReportName.Contains(request.SearchTerm) ||
            (t.Barcode != null && t.Barcode.Contains(request.SearchTerm)));
    }
}

if (request.TestGroupId.HasValue)
    query = query.Where(t => t.TestGroupId != null && t.TestGroupId.Value == request.TestGroupId.Value);
```

> **Case-insensitivity note:** SQLite (the project's database) uses `BINARY` collation by default, so `string.Contains()` is case-sensitive. For case-insensitive search, use `EF.Functions.Like(t.Name, $"%{request.SearchTerm}%")` or apply `.ToLower()` on both sides. Confirm the project's SQLite collation configuration; if using a case-insensitive collation (e.g., `NOCASE`), standard `Contains` suffices.

**Handler pattern** (example: CreateTestCommandHandler):
```csharp
public sealed class CreateTestCommandHandler
    : IRequestHandler<CreateTestCommand, Result<int>>
{
    private readonly IApplicationDbContext _db;

    public CreateTestCommandHandler(IApplicationDbContext db) => _db = db;

    public async Task<Result<int>> Handle(CreateTestCommand request, CancellationToken ct)
    {
        // Duplicate check by Name
        if (_db.Set<Test>().Any(t => t.Name == request.Name.Trim()))
            return Result<int>.Failure(Error.Conflict("اسم التحليل موجود بالفعل"));

        // FK validation for TestGroupId
        if (request.TestGroupId.HasValue &&
            !_db.Set<TestGroup>().Any(g => g.Id.Value == request.TestGroupId.Value))
            return Result<int>.Failure(Error.NotFound("مجموعة التحاليل غير موجودة"));

        // ID is database-generated (IDENTITY + ValueGeneratedOnAdd).
        // Pass dummy ID 0; EF Core overrides it on SaveChanges.
        var test = Test.Create(
            TestId.Create(0), request.Name, request.ReportName, request.ReceiptName,
            request.CompletionDurationMinutes, request.PatientPrice,
            (ResultKind)request.ResultKind, request.IsCultureType,
            request.TestGroupId.HasValue ? TestGroupId.Create(request.TestGroupId.Value) : null,
            request.Barcode, request.IsSentOut, request.SentOutCostPrice, request.LabToLabPrice);

        _db.Add(test);
        await _db.SaveChangesAsync(ct);
        return Result<int>.Success(test.Id.Value);
    }
}
```

> **ID-generation note:** All four tables (Tests, TestGroups, WorkGroupLogs, ReferenceRanges) use SQL Server IDENTITY columns with EF Core `ValueGeneratedOnAdd()`. The `Create(0)` pattern is used because: (1) it avoids the `Max()+1` race condition, (2) it aligns with the standard EF Core pattern for value-generated-on-add properties, and (3) the value is replaced by the database-generated identity after `SaveChangesAsync()`. **Note:** The exact SQL behavior (whether EF Core omits the Id column or includes it with a placeholder) is not verified by static analysis; an integration test against SQL Server is recommended to confirm runtime behavior. This pattern applies to: `CreateTestCommandHandler`, `CreateTestGroupCommandHandler`, `CreateWorkGroupLogCommandHandler`, `CreateReferenceRangeCommandHandler`, and any other handler that inserts into these tables.

**SaveWorkGroupLogItems handler — atomic replace:**
```csharp
public async Task<Result> Handle(SaveWorkGroupLogItemsCommand request, CancellationToken ct)
{
    var log = _db.Set<WorkGroupLog>().FirstOrDefault(w => w.Id.Value == request.WorkGroupLogId);
    if (log is null)
        return Result.Failure(Error.NotFound("مجموعة العمل غير موجودة"));

    // Remove existing items
    var existing = _db.Set<WorkGroupLogItem>()
        .Where(i => i.WorkGroupLogId == log.Id).ToList();
    foreach (var item in existing) _db.Remove(item);

    // Add new items
    foreach (var testId in request.TestIds)
```

## Open Decisions Requiring Owner Approval

These are presented as explicit open questions, not silently resolved. Each one requires the owner's decision before being baked into the implementation.

### Q1 — PatientTitle scope
- **Question:** Should `PatientTitle` (creation / update / deactivation) be included within M-12's scope, or does it belong to a different module (e.g., M02 Patient Registration)?
- **Recommendation:** Keep it out of M-12. Rationale: (a) PatientTitle is patient-entry data, not test-catalog data; (b) M02 is the natural owner since it's where titles are used; (c) including it in M-12 creates scope creep; (d) M02 can define its own PatientTitle CRUD when it's built.
- **Trade-off:** If M02 is built before M-12 ships, M02 will need to either create its own PatientTitle handling or wait. If M-12 is built first, there's no gap since M02 doesn't exist yet.
- **Status:** Open. The plan excludes PatientTitle; the owner may decide otherwise.

### Q2 — Test field update pattern
- **Question:** Should `Test` field edits use separate per-field typed mutators (`Rename`, `SetReportName`, etc.) — finer audit granularity, higher implementation cost — or the existing single bulk `Update` method (simpler, coarser audit granularity)?
- **Recommendation (this plan's current choice):** single bulk `Update` method.
  - *For:* simpler implementation; one command per save action; matches existing codebase pattern; less handler boilerplate; if multiple fields are dirty, fewer transactions.
  - *Against:* coarser audit trail; one method must validate all fields at once.
- **Alternative (Hermes's choice):** per-field typed mutators.
  - *For:* single-responsibility guards; finer audit trail; UI staged-edit pattern maps naturally to per-field commands.
  - *Against:* 10 method names vs. 1; more handler boilerplate; the existing `Test.Update` becomes dead code.
- **Status:** Open. This plan uses bulk `Update`; the owner may switch to per-field mutators.

## Factual Technical Answer (Q3)

**Q3 — Result entity snapshot behavior:** Does the `Result` entity store its own independent copy of the reference-range values and the pass/fail evaluation at the time a result is entered, or does it rely on a live reference to the `ReferenceRange` table?

**Answer (with direct evidence):** No. The current `Result`-equivalent aggregate in the codebase does **not** store any reference-range snapshot. The relevant entities live under `src/TopLab.Domain/Results/`:

- **`src/TopLab.Domain/Results/PatientTest.cs`** (157 lines): the entity exposes `ResultValue` (string), `ResultFlag?` (enum), `Notes` (string?), `EnteredByUserId`, `EnteredAtUtc`, `IsReviewed`, `ReviewedByUserId`, `ReviewedAtUtc`. It does **not** expose any `ReferenceRangeId`, `MinValue`, `MaxValue`, `LowComment`, `HighComment`, `Sex`, `AgeUnit`, `AgeMin`, or `AgeMax` field.
- **`src/TopLab.Domain/Results/ProfileResultItem.cs`** (64 lines): exposes `AnalyteName`, `ResultValue`, `Unit`, `ProfileResultFlag?`, `IsVerified`, `IsPrinted`. No reference-range fields.
- **`src/TopLab.Domain/Results/CultureResult.cs`** and **`CultureAntibioticResult.cs`**: grep-confirmed zero matches for reference-range fields.

**Consequence:** Today, the `PatientTest.ResultValue + ResultFlag` row alone does not carry a frozen reference range. The pass/fail evaluation against a `ReferenceRange` is presumably resolved at query/read time (M04 territory). This means if a `ReferenceRange` is edited after results were entered, historical results would show different pass/fail evaluations — a violation of BR-05/FR-M12-006. The `ReferenceRangeSnapshot` value object introduced in S1 of this plan is the Domain shape that M-04 will need to persist on `Result` rows to fix this gap.

**Source paths cited:**
- `src/TopLab.Domain/Results/PatientTest.cs` (lines 8-66, properties; lines 115-122, `EnterResult` mutator)
- `src/TopLab.Domain/Results/ProfileResultItem.cs` (lines 7-21, properties)
- `src/TopLab.Domain/Results/CultureResult.cs` and `CultureAntibioticResult.cs` (grep-confirmed empty)
