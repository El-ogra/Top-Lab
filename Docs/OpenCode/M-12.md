## Cross-Review Changelog

This file was updated after multiple rounds of cross-review with `Docs/Hermes/M-12.md` and the consolidated `Docs/Final Action Plan for Functional Unit 12.md`. The following items are concrete improvements adopted from those reviews, applied minimally and within this plan's own structure:

- **CR-1 (from Hermes §S1):** Added `ReferenceRangeSnapshot` value object to S1 to handle the freeze contract (BR-05/FR-M12-006). This is a Domain-driven design approach that ensures historical patient results retain their original reference-range values.
- **CR-2 (from Hermes §S1):** Domain events (`TestChangedEvent`) were originally considered as an optional enhancement for finer audit granularity. **Final verdict after cross-review with Final Action Plan:** Domain events are **rejected entirely**. Architectural reasoning: (a) the Domain project has zero external package references — `INotification` comes from MediatR, which cannot be referenced from Domain; (b) the Architecture Blueprint §3 forbids Domain from referencing Application-layer concerns; (c) no domain-event infrastructure (dispatcher, handlers) exists in the codebase. Audit granularity is achieved at the Application layer via command handlers.
- **CR-3 (from Hermes §S8):** Added comprehensive Arabic error-message table to S8 for all M-12 operations.
- **CR-4 (from Hermes §S3):** Improved ID-generation strategy: replaced `Max()+1` pattern with `TestId.Create(0)`. **Rationale:** (1) avoids the `Max()+1` race condition where concurrent inserts could compute the same next ID, (2) follows the standard EF Core pattern for value-generated-on-add properties, (3) the actual ID is database-generated via IDENTITY and read back by EF Core after `SaveChangesAsync()`. **Note:** Both patterns (`Max()+1` and `Create(0)`) may work on SQL Server; the `Create(0)` choice is based on cleanliness and race-condition avoidance, not on proven failure of `Max()+1`. An integration test is recommended to confirm runtime behavior.
- **CR-5 (from Final Action Plan):** Adopted PatientTitle in M-12 scope (D-1). PatientTitle is a lookup/enum-like entity with 3 rows; including it avoids orphaning a dependency that M02 (Patient Registration) would need. Added PatientTitle CRUD commands, queries, and ViewModel.
- **CR-6 (from Final Action Plan):** Corrected feature folder name from `TestsAndReferenceRanges` to `TestCatalogAndReferenceRanges` per Module Dependency Map (D-5).
- **CR-7 (from Final Action Plan):** Adopted SQLite → SQL Server collation corrections: all search filters use SQL Server case-insensitive collation (SQL_Latin1_General_CP1_CI_AS); `EF.Functions.Like` for text search instead of `.Contains()` with `.ToLower()`.

- **CR-10 (from Final Action Plan):** Adopted ReferenceRange.Update mutator added to S1 for consistency with the update command pattern.

## Executive Summary

Module M-12 delivers the Test Catalog management screen and Reference Range configuration for the TopLab laboratory information system. This module touches all four Clean Architecture layers and involves seven domain entities (`Test`, `TestGroup`, `ReferenceRange`, `TestComment`, `WorkGroupLog`, `WorkGroupLogItem`, `PatientTitle`). The existing domain entities already have `Create` factory methods and some have `Update`; this plan fills the behavioral gaps, builds the full Application query/command surface, and delivers the WPF Presentation layer.

## Slice S1 — Domain Behaviors (Mutators + Invariant Guards)

### Description
Complete the domain entity behavior methods that are currently missing or incomplete. Add `Update` methods, collection management methods, invariant guards, and the `ReferenceRangeSnapshot` value object for the freeze contract (BR-05/FR-M12-006). This slice has zero external dependencies — it is pure domain logic.

> **Freeze Contract (BR-05/FR-M12-006):** When a result is entered, the reference-range values active at that moment must be preserved independently of any later changes to the `ReferenceRange` table. The `ReferenceRangeSnapshot` value object captures this frozen state. The actual persistence of this snapshot on `Result` rows is M-04's responsibility (per ambiguity #5); M-12 only defines the Domain shape.

> **Note on `WorkGroupLogItem` constructor:** The current public parameterless constructor is required by EF Core, but the public parameterized constructor should be made private. A static `Create(...)` factory method replaces it. Verify that no existing code calls the public parameterized constructor before making this change. The private parameterless constructor remains for EF Core materialization.

> **Note on `TestComment.Update`:** This method is added here for completeness, but `TestComment` write commands (CRUD) belong to Module M-13 per FR-M13-002. Only the domain method is added in S1; no Application-layer commands for `TestComment` are created in M-12.

> **Note on `PatientTitle.Update`:** PatientTitle is a simple lookup entity with ~3 rows (Mr., Mrs., Miss). The `Update` method allows renaming if needed. PatientTitle CRUD is included in M-12 scope (D-1) because: (a) it's a dependency that M02 (Patient Registration) would need, (b) including it here avoids orphaning a lookup that no module owns.

**GetTestCatalogQuery:**
```csharp
public sealed record GetTestCatalogQuery(
    string? SearchTerm = null,
    int? TestGroupId = null) : IRequest<Result<IReadOnlyList<TestSummaryDto>>>;
```

Handler filters by `SearchTerm` against `Name`, `ReportName`, `Barcode`, `TestGroupName` (CR-9), and `Test Number` (Contains, SQL Server case-insensitive collation). Filters by `TestGroupId` if provided. **Test number search:** attempt `int.TryParse(SearchTerm)` — if successful, include tests where `t.Id.Value == parsedInt` in the filter (OR logic with text matches). Uses `_db.Set<Test>()` with `.Include`-free projection (join via TestGroupId). Returns `Result<IReadOnlyList<TestSummaryDto>>`.

```csharp
// Pseudo-code for search filter (SQL Server collation — CR-7):
var query = _db.Set<Test>().AsQueryable();

if (!string.IsNullOrWhiteSpace(request.SearchTerm))
{
    var term = request.SearchTerm.Trim();

    if (int.TryParse(term, out int testNumber))
    {
        query = query.Where(t =>
            EF.Functions.Like(t.Name, $"%{term}%") ||
            EF.Functions.Like(t.ReportName, $"%{term}%") ||
            (t.Barcode != null && EF.Functions.Like(t.Barcode, $"%{term}%")) ||
            EF.Functions.Like(t.TestGroup.Name, $"%{term}%") ||  // CR-9: group-name axis
            t.Id.Value == testNumber);
    }
    else
    {
        query = query.Where(t =>
            EF.Functions.Like(t.Name, $"%{term}%") ||
            EF.Functions.Like(t.ReportName, $"%{term}%") ||
            (t.Barcode != null && EF.Functions.Like(t.Barcode, $"%{term}%")) ||
            EF.Functions.Like(t.TestGroup.Name, $"%{term}%"));  // CR-9: group-name axis
    }
}

if (request.TestGroupId.HasValue)
    query = query.Where(t => t.TestGroupId != null && t.TestGroupId.Value == request.TestGroupId.Value);
```

> **SQL Server collation note (CR-7):** The project uses SQL Server with default collation `SQL_Latin1_General_CP1_CI_AS` (case-insensitive, accent-insensitive). `EF.Functions.Like` is used instead of `.Contains()` for explicit case-insensitive behavior that is guaranteed regardless of connection-level collation settings. No `.ToLower()` calls are needed.

**Handler pattern** (example: CreateTestCommandHandler):
```csharp
public sealed class CreateTestCommandHandler
    : IRequestHandler<CreateTestCommand, Result<int>>
{
    private readonly IApplicationDbContext _db;

    public CreateTestCommandHandler(IApplicationDbContext db) => _db = db;

    public async Task<Result<int>> Handle(CreateTestCommand request, CancellationToken ct)
    {
        // Duplicate check by Name
        if (_db.Set<Test>().Any(t => t.Name == request.Name.Trim()))
            return Result<int>.Failure(Error.Conflict("اسم التحليل موجود بالفعل"));

        // FK validation for TestGroupId
        if (request.TestGroupId.HasValue &&
            !_db.Set<TestGroup>().Any(g => g.Id.Value == request.TestGroupId.Value))
            return Result<int>.Failure(Error.NotFound("مجموعة التحاليل غير موجودة"));

        // ID is database-generated (IDENTITY + ValueGeneratedOnAdd).
        // Pass dummy ID 0; EF Core overrides it on SaveChanges.
        var test = Test.Create(
            TestId.Create(0), request.Name, request.ReportName, request.ReceiptName,
            request.CompletionDurationMinutes, request.PatientPrice,
            (ResultKind)request.ResultKind, request.IsCultureType,
            request.TestGroupId.HasValue ? TestGroupId.Create(request.TestGroupId.Value) : null,
            request.Barcode, request.IsSentOut, request.SentOutCostPrice, request.LabToLabPrice);

        _db.Add(test);
        await _db.SaveChangesAsync(ct);
        return Result<int>.Success(test.Id.Value);
    }
}
```

> **ID-generation note (CR-4):** All four tables (Tests, TestGroups, WorkGroupLogs, ReferenceRanges) use SQL Server IDENTITY columns with EF Core `ValueGeneratedOnAdd()`. The `Create(0)` pattern is used because: (1) it avoids the `Max()+1` race condition, (2) it aligns with the standard EF Core pattern for value-generated-on-add properties, and (3) the value is replaced by the database-generated identity after `SaveChangesAsync()`. **Note:** Both patterns (`Max()+1` and `Create(0)`) may technically work on SQL Server; the `Create(0)` choice is based on cleanliness and race-condition avoidance, not on proven failure of `Max()+1`. An integration test against SQL Server is recommended to confirm runtime behavior. This pattern applies to: `CreateTestCommandHandler`, `CreateTestGroupCommandHandler`, `CreateWorkGroupLogCommandHandler`, `CreateReferenceRangeCommandHandler`, `CreatePatientTitleCommandHandler`, and any other handler that inserts into these tables.

public async Task<Result> Handle(SaveWorkGroupLogItemsCommand request, CancellationToken ct)
{
    var log = _db.Set<WorkGroupLog>().FirstOrDefault(w => w.Id.Value == request.WorkGroupLogId);
    if (log is null)
        return Result.Failure(Error.NotFound("مجموعة العمل غير موجودة"));

    // Remove existing items
    var existing = _db.Set<WorkGroupLogItem>()
        .Where(i => i.WorkGroupLogId == log.Id).ToList();
    foreach (var item in existing) _db.Remove(item);

    // Add new items
    foreach (var testId in request.TestIds)
    {
        if (!_db.Set<Test>().Any(t => t.Id.Value == testId))
            return Result.Failure(Error.NotFound($"التحليل {testId} غير موجود"));
        _db.Add(WorkGroupLogItem.Create(log.Id, TestId.Create(testId)));
    }

    await _db.SaveChangesAsync(ct);
    return Result.Success();
}

**Consequence:** Today, the `PatientTest.ResultValue + ResultFlag` row alone does not carry a frozen reference range. The pass/fail evaluation against a `ReferenceRange` is presumably resolved at query/read time (M04 territory). This means if a `ReferenceRange` is edited after results were entered, historical results would show different pass/fail evaluations — a violation of BR-05/FR-M12-006. The `ReferenceRangeSnapshot` value object introduced in S1 of this plan is the Domain shape that M-04 will need to persist on `Result` rows to fix this gap.
