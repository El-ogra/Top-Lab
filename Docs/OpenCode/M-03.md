## 2. Module 3 — Patient Billing & Account Settlement (backend only)

> Self-contained plan. Baseline: pinned commit `70f145e` + assumed-future M02/M21 surface (the pieces this module uses are re-stated below). **All of this module's rules are settled requirements:** the balance formula (inlined in full below — Data Model §7.1 + ADR-0016 + FR-M03-001/003/004); void-and-reissue-only correction of payment operations, never physical delete, no edit-in-place (ADR-0017 binding + Coding Standards §7.4 binding); the void/correction gate on `CASH_DISBURSE_DEPOSIT` (FR-M17-004 item 11, whose documented scope explicitly includes patient accounting «محاسبة المرضى»); and discount-limit enforcement as a per-user percent cap against `User.DiscountLimitPercent` at the application layer with a `Validation` failure on breach (Data Model §13 BR-06 + FR-M03-006/BR-06 + FR-M17-004 item 7 + Test Strategy §3.2/§7.2). Feature folder name: `PatientBilling` (new; consistent with the existing per-feature folder convention).

### 2.1 Module 3 context — what exists and what is assumed (inlined)

- **Existing at `70f145e` (re-verified):** `PaymentOperation : AuditableEntity<PaymentOperationId>` (`src/TopLab.Domain/Billing/PaymentOperation.cs`) — `PatientId`, `Amount (decimal 18,2)`, `DiscountAmount? (decimal 18,2)`, `IsExtraCharge (bool)`, `OperationType { Payment=0, Correction=1, FullSettlement=2 }` (tinyint), `ReceivedByUserId (int)`, `OperationAtUtc (datetime2)`, `IsVoided`; mutators `Create(id, patientId, amount, receivedByUserId, operationAtUtc, discountAmount = null, isExtraCharge = false, operationType = Payment)` and `Void()` — **both guard-free** (`Create` accepts negative amounts and discounts > amount today). Configuration re-verified: identity PK, FK `PaymentOperation → Patient` Cascade, index on `PatientId`. Existing Domain tests: `Create_Valid`, `Void_Sets` only (`tests/TopLab.Domain.Tests/Billing/PaymentTests.cs`, re-verified). `User.DiscountLimitPercent` (0–100, `SetPolicy`) exists (re-verified) and is the documented enforcement target for the discount limit (Data Model §13 BR-06). Permission codes needed (`CASH_DISBURSE_DEPOSIT` id 11) already seeded. `ReceiptSettings.Currency` default `"L.E."` (re-verified). `Test.ReceiptName` exists (max 150, required — re-verified in `TestConfiguration`) and is the receipt-facing test name. `CashMovement` (treasury) exists but is out of this module's scope.
- **Assumed from M02 (inlined):** `Patient.IsDeleted` exists (`bit not null default 0` + index); `PatientTest` rows carry `PriceAtOrderTime`; result-recorded tests cannot be removed (hard-delete forbidden once `EnteredAtUtc` is set — so the price basis is stable once entered); `PatientRegistrationAccessPolicy` exists (this module ships its own policy class, does not import M02's).
- **Balance formula (settled — inlined in full, per independence):** `TotalCharged = Σ PatientTest.PriceAtOrderTime + Σ (PaymentOperation.Amount where !IsVoided && IsExtraCharge)`; `TotalPaid = Σ (PaymentOperation.Amount + coalesce(DiscountAmount, 0) where !IsVoided && !IsExtraCharge)`; `Balance = TotalCharged − TotalPaid` (negative = credit, no clamping). `Correction` rows contribute to `TotalPaid` (positive Amount = credit — stated engineering pin); `FullSettlement` rows contribute as ordinary payments whose `Amount` equals the balance at settlement time (FR-M03-004); voided rows contribute nothing. Reference corroboration: `RLS_Learn.pdf` §1-2 (extra charge "+"-prefixed onto the tests total; discount entered with the payment; «خالص» settles in full).
- **Not in scope:** treasury/cash-drawer movements (`CashMovement` belongs to the later treasury module M19-territory; this module records patient payments only, in `PaymentOperations`); payment editing — **settled: no edit command ships; a mis-recorded amount is corrected by voiding the row and re-recording (ADR-0017).**

### 2.4 Module 3, Slice 3 — Application write surface: record payment (with optional discount), extra charge, correction, full settlement, void

### 2.8 Module 3 — Risks and Mitigations

| Risk | Mitigation |
|---|---|
| `PaymentOperation.Create` guard additions break an existing caller | Guards are additive-only; the F5 baseline has no Application callers of `Create` (no billing feature exists at `70f145e` — verified by feature-folder listing); the two existing Domain tests use valid inputs. |
| Reference-system users expect edit/delete of payments (legacy muscle memory) | Settled by binding documentation (ADR-0017 + Coding Standards §7.4): void + re-record is the only correction flow; handoff documents it; the friendly `العملية ملغاة بالفعل.` conflict keeps the UI honest; the S-04 reconciliation note is in the close-out ADR. |
| Deleted `User` row breaks `ReceivedByUserName` resolution | Stated fallback rule (raw id string) + a dedicated handler test. |
| Balance formula drift between this module's calculator and the other four modules' private probes | The formula text is identical by construction (a single drafting source, documentation-settled); the close-out ADR pins it; each consumer's tests assert the same worked example (prices 100+50, extra charge 20, payment 80 with discount 10, voided payment 999 ⇒ Charged 170, Paid 90, Balance 80). |
| The id-11 void/correction gate is a scope reading, not a verbatim quote | Recorded honestly in the close-out ADR (FR-M17-004 item 11's documented scope includes patient accounting; no other catalog item covers payment correction); the owner can re-point the gate by editing one constant in `PatientBillingAccessPolicy` with zero structural change. |
