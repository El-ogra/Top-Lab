## 0) The boundary rule this plan followed

### 0.1 The rule, stated exactly

> **A function belongs to Wave 2 if and only if it can be executed, exactly as originally specified, without creating any new migration file and without editing any existing migration file. A function that requires a migration belongs to Wave 3. The boundary is the migration, not the behaviour.**

### 0.2 What was tested, function by function

Each of the original Wave 2 candidates was tested against the code for "does executing this, as specified, require a column?" The answer — not a judgement about elegance — decided the wave.

| Original Wave 2 item | Does it require a column, as specified? | Result |
|---|---|---|
| **EN-1** — three-code patient identity, 13-digit | The reference issues **three distinct persistent codes** per patient (REF3 p.18): a case/day code, a **file code** stuck on the envelope, and a lab code. These are identifiers, not computed renderings. Storing them is the specified behaviour. | **Wave 3** — new patient-code columns |
| **B-4** — barcode symbology **catalogue**, configurable | A *catalogue* is stored rows. `BarcodeLabelRenderer` hard-codes `BarcodeFormat.CODE_128`; making it catalogue-driven means a table to read from. | **Wave 3** — symbology catalogue table |
| **A-3** — per-test tube & container labels | The per-test material attribute already exists (`Test.Barcode`). But the specified label window includes a **saved** position adjustment: REF3 p.20 §5 — adjust the barcode position with sliders, print, *"وبعد الوصول للأبعاد المطلوبة اضغط زر **حفظ**"* ("when you reach the required dimensions press **Save**"). A save with nowhere to persist is not the specified function. **No label layout or position is stored anywhere in the code today.** | **Wave 3** — label layout/position storage; also depends on EN-1 and B-4 |
| **A-18** — barcode on the receipt and envelope | `ReceiptSettings` has **no** barcode member (verified: `TopMarginCm`, `Currency`, `PickupTimeDefault`, `PrintOnce`, `TestDetailDisplayMode`, `CashierPrinterEnabled`, `HeaderFooterMode`). `EnvelopeSettings` has **no** barcode member. The optional toggle the reference specifies (RLShow p.3) is a **new boolean column on both**. It also consumes the EN-1 file code. | **Wave 3** — two settings columns; depends on EN-1 |
| **A-12** — reprint a single barcode label independently | The specified behaviour is REF3 p.16 §14: on a **lost patient card**, search the patient and *"طباعة الباركود الخاص به مرة اخري وال يعطى رقم اخر جديد"* — print his barcode again, **do not issue a new number**. `PrintBarcodeCommand(int PatientId)` already exists, is fully implemented and is already tested; it is simply **not reachable from the search window**. Adding an entry point is **no schema change**. | **Wave 2 — S4** |

**The boundary removes four of the five original Wave 2 items.** That is the honest consequence of applying the rule, and it is stated rather than papered over.

### 0.3 On the withdrawn package

The previous P-02 package kept the migration-requiring functions inside Wave 2 by **changing where their state lives** — deriving the patient codes instead of storing them, and moving the symbology and toggles to a workstation-local JSON file. That changed the scope of the settings, the semantics of the features and the location of their state, and it was not authorised. **Those functions are not re-designed here and are not in this wave.** They appear in §7 as Wave 3 work, to be executed as originally specified, with their migrations.

### 0.4 Nothing was moved in by changing behaviour

No function in this wave was made migration-free by altering how it works. Where a function could only be made migration-free by redesign, it was **moved to Wave 3** (RD-5).

## 4) S1 — `PatientReportPdfExporter` sets the QuestPDF licence (D-1) — **no migration**

### Scope
```
Modified:
  src/TopLab.Infrastructure/Services/PatientReportPdfExporter.cs
  (tests only)
```

**Migration required: NONE.** One production file, no EF configuration, no persistence.

### The defect
`QuestPDF.Settings.License` is process-global. Six writers set it in a static constructor — `CustomGroupPdfWriter`, `InvoicePdfWriter`, `PriceListPdfWriter`, `ReceiptPdfWriter`, `ReportPdfWriter`, `WorkSheetPdfWriter` — each setting `Settings.License = LicenseType.Community` and `Settings.UseSystemFonts = true`. `PatientReportPdfExporter` is the **only** QuestPDF entry point with **no static constructor**. Run in isolation it throws:

```
System.Exception : Please configure the QuestPDF license by setting
'QuestPDF.Settings.License' at application startup.
```

In production the behaviour is order-dependent: whether "export patient report to PDF" works depends on whether the user printed something else first in the session.

### Implementation
1. Add a `static PatientReportPdfExporter()` constructor setting the same two lines. `PriceListPdfWriter`'s XML comment already records the lesson: *"each writer sets the licence in its OWN static constructor and must not rely on another writer running first."*
2. **Change nothing else.** No behaviour change, no signature change, no refactor of the other six writers, no shared licence helper — that would be a new abstraction this wave does not need.

## 6) S3 — Sequenced, error-surfacing filter reload (D-3) — **no migration**

### Scope
```
Modified:
  src/TopLab.Presentation/ViewModels/Patients/PatientSearchViewModel.cs
Added:
  tests/TopLab.Presentation.Tests/PatientSearch/FilterReloadSequencingTests.cs
```

**Migration required: NONE.** One ViewModel; no entity, no configuration, no persistence.

### The defect
`OnFilterChanged()` does `_ = ReloadFromFirstPageAsync()`; `SearchAsync` has **no `catch`**. Two consequences: a database fault during a filter change is silently lost, and a burst of filter changes (the age `TextBox`es fire on `LostFocus`) can complete out of order, letting a stale query overwrite a newer result set.

### Implementation
1. Introduce a private `CancellationTokenSource?` — or a monotonically increasing generation counter; pick one and record which in the memory file. Cancel or supersede the previous in-flight search before starting the next.
2. Wrap the reload body in `try` / `catch`. On failure set `ErrorMessage` through `ResultErrorPresenter` and leave the list untouched. **Never** discard a task whose failure can be lost.
3. Clear the cancellation source in a `finally`.
4. Treat `OperationCanceledException` as cancellation, not an error — do not surface it.
5. **Do not** refactor the six other `_ = SomethingAsync()` sites (C-6 / RD-3). This slice fixes the filter path only.

### VG-03
- [ ] Build 0/0 · no test count below baseline
- [ ] A handler that throws ⇒ `ErrorMessage` is populated and the previous list survives
- [ ] A rapid burst of filter changes displays the **last** requested filter set
- [ ] `OperationCanceledException` does **not** surface as an error
- [ ] S2's age-field tests and `PatientSearch_FilterChangeResetsToFirstPage` still green
- [ ] The six pre-existing `_ =` sites are untouched — `git diff` shows only this file
- [ ] **No migration:** `git diff -- src/TopLab.Infrastructure/Persistence/` empty (SD-3)

4. Reuse `IBarcodeService`; do not widen it. The configurable symbology catalogue is **B-4, and B-4 is Wave 3**.
5. The control is presented as a reprint of the selected patient's card barcode — the reference's lost-card flow.
