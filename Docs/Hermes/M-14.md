| # | Ambiguity | Resolution (chosen approach) | Evidence / reasoning |

| 1 | Should the empty-referral-field default behavior depend on `SystemSettings`? | **No.** The default is a pure static resolver returning `"Himself"`/`"Herself"` from `Sex`, with NO settings dependency. | Owner-settled decision 1. | 3 | Should `GeneratedIdCode` uniqueness be a DB unique index? | **No.** Application/handler-level uniqueness only (pre-check + unique-violation catch + bounded retry). | Owner-settled decision 3. `ExternalEntityConfiguration` has no unique index on `GeneratedIdCode`; no migration will add one. |
| 4 | Should multiple placeholder styles (e.g., secondary/legacy "المريض نفسه") be supported? | **No.** Only the sex-based Himself/Herself default. | Owner-settled decision 4. |

## Slices

### S1 — Domain mutators + invariants (Domain layer)

- **Title:** Add `Update`, `Delete`, `GenerateIdCode`, and `SetPriceList` mutators to `ExternalEntity` with full invariant guards.
- **User-visible behavior or technical capability:** Enables the Application layer to edit an entity (including type transitions while preserving guard invariants), delete one with caller-driven reference checks, and generate a unique `GeneratedIdCode` on demand. All guards are enforced inside entity methods; the Application layer cannot reach an invalid state.
- **Layer(s) touched:** Domain. Adds public methods to `src/TopLab.Domain/ExternalEntities/ExternalEntity.cs`; new unit tests in `tests/TopLab.Domain.Tests/ExternalEntities/ExternalEntityTests.cs`.
- **Full-stack reasoning:** The aggregate is incomplete (`Create` exists; mutators do not). All cross-field guards (treating-doctor-cannot-have-price-list, referral-or-contract-must-have-price-list, contact-fields-all-optional, percent-range 0–100) must live in the Domain so validators and handlers can call them without re-implementing business rules. `Delete` is a state-clearing mutator that throws a `DomainException` if the caller signals reference presence (the caller is the Application handler that has just queried `Patients` and `SentOutSamples`; the Domain layer has no EF dependency and therefore cannot query references itself).
- **Validation Gate:** xUnit `ExternalEntityTests.Update_ChangesNameAndContactFields_PreservesGuards` asserts that calling `Update(...)` with new values re-applies the treating-doctor/price-list guard: a `TreatingDoctor` cannot be `Update`d with `priceListId != null` and a `ReferralOrContract` cannot be `Update`d with `priceListId == null`. Companion test `Update_FromTreatingDoctorToReferralOrContract_WithMatchingPriceList_Succeeds` confirms a valid type-transition succeeds and re-validates all guards. `Delete_WhenCallerSignalsReferences_Throws` confirms the Domain surfaces a `DomainException` for reference-present deletes. `GenerateIdCode_WhenCodeIsNull_SetsGeneratedIdCode` and `GenerateIdCode_WhenCodeAlreadySet_NoOp` confirm idempotency. `tests/TopLab.Domain.Tests/ExternalEntities/ExternalEntityTests.cs` is the file path; whole-project Domain coverage floor ≥ 90% is satisfied for the M-14 footprint.
- **Exit criteria (additional):** `dotnet build src/TopLab.Domain` clean; zero new packages; no Domain references to MediatR or EF Core; existing `Create` factory signature unchanged.

### S3 — Application write surface (Application layer)

- **Title:** Commands, handlers, validators for create / update / delete / ID-generation, plus the empty-referral-field default resolver.
- **User-visible behavior or technical capability:** Lets an authorized caller (`EDIT_SYSTEM_SETTINGS`) create, update (with type-transition re-validation), delete (uniform guarded hard-delete), and trigger ID-generation on an `ExternalEntity`. Also exposes the pure `ReferralNameResolver` static function used by reporting consumers when a patient's referral field is empty.
- **Layer(s) touched:** Application. Adds:
  - `src/TopLab.Application/Features/ExternalEntities/Commands/CreateExternalEntity/CreateExternalEntityCommand.cs` + `Handler` + `Validator`
  - `Commands/UpdateExternalEntity/UpdateExternalEntityCommand.cs` + `Handler` + `Validator`
  - `Commands/DeleteExternalEntity/DeleteExternalEntityCommand.cs` + `Handler` + `Validator`
  - `Commands/GenerateEntityIdCode/GenerateEntityIdCodeCommand.cs` + `Handler` + `Validator`
  - `Common/ReferralNameResolver.cs` (static pure method `Resolve(string? referralName, Sex patientSex) -> string`)
  - `Common/Interfaces/IEntityIdCodeGenerator.cs` + `Infrastructure/Services/RandomEntityIdCodeGenerator.cs` (default implementation behind the interface, injected into `GenerateEntityIdCodeCommandHandler`)
  - Tests under `tests/TopLab.Application.Tests/Features/ExternalEntities/Commands/` mirroring the command folders.
- **Full-stack reasoning:** Every command implements `IAuthorizedRequest` with `RequiredPermissionCode = "EDIT_SYSTEM_SETTINGS"` (consistent with M22 and M12 reference-data commands; verified by `src/TopLab.Application/Common/Authorization/IAuthorizedRequest.cs` and the `AuthorizationBehavior` pipeline). Handlers depend only on `IApplicationDbContext`. Validators enforce input bounds (name length, contact-field lengths, percent range 0–100, `EntityType` ∈ {TreatingDoctor, ReferralOrContract, PartnerLab}, `PriceListId` existence check for ReferralOrContract only). `DeleteExternalEntityCommandHandler.Handle` queries `Patients` (count `TreatingDoctorId == id || ReferralEntityId == id`) and `SentOutSamples` (count `ExternalLabEntityId == id`) before calling `ExternalEntity.Delete(...)`; if either count is > 0, returns `Error.Conflict("لا يمكن حذف الجهة لوجود مرضى أو عينات مرتبطة بها")`. `GenerateEntityIdCodeCommandHandler.Handle` calls `IEntityIdCodeGenerator.GenerateAsync(...)` to produce a candidate code, runs an existence pre-check (`_db.Set<ExternalEntity>().Any(e => e.GeneratedIdCode == candidate)`), and on `SaveChangesAsync` catches the SQL unique-violation exception (defense-in-depth) and retries up to a bounded N times (e.g., 5). `ReferralNameResolver.Resolve(string? referralName, Sex patientSex)` returns the input if non-empty, otherwise `"Himself"` for `Male` and `"Herself"` for `Female` — frozen literals, no EF, no MediatR, no settings dependency, no localization-provider dependency (per owner decision 1 and 4). `IEntityIdCodeGenerator` is registered in `src/TopLab.Application/DependencyInjection.cs` (consistent with the established pattern: `services.AddScoped<IEntityIdCodeGenerator, RandomEntityIdCodeGenerator>();`).
- **Validation Gate:** xUnit `DeleteExternalEntityCommandHandlerTests.Handle_WhenReferencedByPatient_ReturnsConflictError` seeds the fake `IApplicationDbContext` with a `Patient` whose `TreatingDoctorId == id` and asserts the handler returns `Result.Failure(Error.Conflict(...))` without calling `SaveChangesAsync`. Companion test `Handle_WhenReferencedBySentOutSample_ReturnsConflictError` confirms the same guard for `SentOutSample.ExternalLabEntityId`. `Handle_WhenNotReferenced_DeletesEntity_ReturnsSuccess` confirms the happy path. `GenerateEntityIdCodeCommandHandlerTests.Handle_WhenCodeAlreadyExists_RetriesAndSucceeds` seeds a colliding `GeneratedIdCode` and asserts the handler retries and persists a fresh code. `ReferralNameResolverTests.Resolve_WhenReferralNameIsNullAndPatientIsMale_ReturnsHimself` and `Resolve_WhenReferralNameIsNullAndPatientIsFemale_ReturnsHerself` lock the resolver literals. `CreateExternalEntityCommandValidatorTests` asserts the `ReferralOrContract` without `PriceListId` and the `TreatingDoctor` with `PriceListId` cases fail validation with the Arabic messages `"يجب اختيار قائمة أسعار للجهة المحولة/المتعاقدة"` and `"الطبيب المعالج لا يحق له قائمة أسعار"`. Handler test files live under `tests/TopLab.Application.Tests/Features/ExternalEntities/Commands/<UseCase>/`.
- **Exit criteria (additional):** No new EF migration; no Infrastructure-layer changes beyond the `IEntityIdCodeGenerator` registration (which belongs to the Application DI wiring but its concrete `RandomEntityIdCodeGenerator` lives in Infrastructure for the EF-untouched rule); no Domain references to MediatR; no Presentation-layer references.

## Evidence-Resolved Decision Log

- **D-1** [Decision]: Add `Update`/`Delete`/`GenerateIdCode`/`SetPriceList` mutators to the existing `ExternalEntity` aggregate instead of creating a new aggregate. **Evidence:** `src/TopLab.Domain/ExternalEntities/ExternalEntity.cs` lines 1–89 (aggregate already exists with `EntityType`, all contact fields, `PriceListId`, `DiscountOrCommissionPercent`, `GeneratedIdCode`; only mutators are missing). **Alternative considered:** Split into per-type aggregates (`TreatingDoctor`, `ReferralOrContract`, `PartnerLab`). Rejected because the F5 schema is a single `ExternalEntities` table with `EntityType tinyint` (per `ExternalEntityConfiguration.cs` line 14) and five downstream consumers (M13, M02, M16, M19, M20) all reference a single `ExternalEntityId`.
- **D-2** [Decision]: No new EF Core migration for M14's core entities; the F5 baseline migration `20260828052248_BaselineDataModel.cs` is sufficient. **Evidence:** `src/TopLab.Infrastructure/Persistence/Configurations/ExternalEntityConfiguration.cs` lines 1–28 and the F5 baseline migration verified in `Docs/Source/Top_Lab_Module_Dependency_Map.md` §2 + post-M22 doc §3.5 row 10. **Alternative considered:** Adding a migration for the contact-field lengths or for `HasIndex(e => e.EntityType)`. Rejected because both are already present in the existing configuration; no schema change is needed.
- **D-3** [Decision]: `EDIT_SYSTEM_SETTINGS` is the permission gate for all M14 commands. **Evidence:** `src/TopLab.Application/Features/SystemAndPrintSettings/Commands/UpdateSystemSettings/UpdateSystemSettingsCommand.cs` lines 14–17 and `src/TopLab.Application/Features/TestCatalogAndReferenceRanges/Commands/CreateTest/CreateTestCommand.cs` (same gate). **Alternative considered:** Defining a new permission code `EDIT_EXTERNAL_ENTITIES`. Rejected because no new permission catalog entry is needed for a reference-data management surface that fits under `EDIT_SYSTEM_SETTINGS`.
- **D-4** [Decision]: `ReferralNameResolver.Resolve(string?, Sex)` is a static pure method in the Application layer with frozen literals `"Himself"`/`"Herself"`. **Evidence:** Owner-settled decision 1 and 4; reference PDF pages 3-11 (`Docs/M14_External_Entities_Reference_Pages.pdf`) showing the lookup-by-code workflow supports the FR-M14-005 reading but not a settings-driven default. **Alternative considered:** Reading the default from `SystemSettings` (FR-M14-006's literal reading). Rejected by owner decision 1; the settings dependency belongs in the M02 patient-entry consumer, not in M14.
- **D-5** [Decision]: Delete is a uniform guarded hard-delete across all three types, blocked when referenced by Patient (`TreatingDoctorId` or `ReferralEntityId`) or by `SentOutSample.ExternalLabEntityId`. **Evidence:** Owner-settled decision 2; existing FKs in `PatientConfiguration.cs` lines 28–29 and `SentOutSampleConfiguration.cs` line 20 (`OnDelete(Restrict)` for `ExternalLabEntityId` is enforced at the DB level too). **Alternative considered:** Per-type delete rules (e.g., soft-delete for treating doctors). Rejected because the owner settled on one uniform rule and soft-delete contradicts the existing `OnDelete(Restrict)` for sent-out samples.
- **D-6** [Decision]: Uniqueness of `GeneratedIdCode` is enforced only at the Application handler level (pre-check + unique-violation catch + bounded retry). **Evidence:** Owner-settled decision 3; `ExternalEntityConfiguration.cs` does not declare a unique index on `GeneratedIdCode`. **Alternative considered:** Adding a unique index via a migration. Rejected by owner decision 3.
- **D-7** [Decision]: The `IEntityIdCodeGenerator` interface lives in the Application layer (`src/TopLab.Application/Features/ExternalEntities/Common/Interfaces/`) with a default implementation `RandomEntityIdCodeGenerator` in Infrastructure (`src/TopLab.Infrastructure/Services/`), registered via `src/TopLab.Infrastructure/DependencyInjection.cs`. **Evidence:** Established Application/ Infrastructure boundary pattern from M22 (`IReportPrintingService` lives in Application; concrete implementation lives in Infrastructure). **Alternative considered:** Putting the generator entirely in the Application layer. Rejected because random number generation may evolve and the swap should be a single DI change; the Application layer must not depend on infrastructure-specific utilities.
