# M-12 — Test Catalog & Reference Ranges Plan

## Cross-Review Changelog

This file was updated after a head-to-head comparison with `Docs/OpenCode/M-12.md`. The following items are concrete improvements adopted from that comparison, applied minimally and within this plan's own structure. They are noted here so the rationale is traceable, not so they override the plan's original decisions.

- **CR-1 (from OpenCode §S8 lines 940 + 947-969):** The plan's S8 acceptance gate now explicitly references the existing `AuditableEntitySaveChangesInterceptor` (delivered in F2/F4 per the "Identifying and understanding the next stage" report §3.1) and the fact that it automatically increments `ModificationCount` on `SaveChangesAsync`. The earlier draft mentioned only "audit-log entries exist" without naming the mechanism. *Why it matters:* the gate is observable only if the interceptor is the verified mechanism; naming it ties the gate to real, already-shipped code rather than to an abstract "audit happens somewhere."
- **CR-2 (from OpenCode §S3 lines 417-425):** S3 Infrastructure now specifies an explicit ID-generation strategy for new `Test`, `TestGroup`, `WorkGroupLog`, and `ReferenceRange` rows. The earlier draft assumed IDs were provided by the caller without stating where they came from. *Why it matters:* the project uses strongly-typed ID factories (`TestId.Create(newId)`, etc.) and EF's F5 baseline does not provide identity columns for the F5 schema-first tables; the ID strategy is a real implementation concern that must be specified.
- **CR-3 (from OpenCode §S1 lines 32 + 70-83):** S1 now explicitly notes that `WorkGroupLogItem`'s public parameterized constructor must be made private (with a static `Create(WorkGroupLogId, TestId)` factory added) and that the pre-check (search for `new WorkGroupLogItem(` callers in the codebase) must be done before making the change, because the public parameterless constructor must remain for EF Core materialization. *Why it matters:* without this pre-check, an M-12 implementation could break M17 (Users), M22 (System Settings), or any other module that constructs `WorkGroupLogItem` directly today. The constraint is real, not theoretical.
- **CR-4 (from OpenCode §S2 lines 195-222):** S2 (Application read surface) now specifies the `SearchTerm` parsing rule: the query attempts `int.TryParse(SearchTerm)` — on success, the search includes a numeric comparison `t.Id.Value == parsedInt` joined with OR to the text matches on `Name` / `ReportName` / `Barcode`. The earlier draft mentioned "partial match" without surfacing the numeric-vs-text distinction that FR-M12-001 explicitly requires ("searchable by test name, containing group, or **test number**"). *Why it matters:* FR-M12-001 names "test number" as a distinct search axis; without the numeric parse, users can never search by the auto-incrementing `Id`.
- **CR-5 (from OpenCode §S7 lines 859-873):** S7 (Presentation — gated features) now specifies that the "النظام" navigation entry in the ShellViewModel must be gated by the existing M17 secondary-password dialog (`ShowSecondaryPasswordDialogAsync`) before opening the TestCatalog. The earlier draft treated the test-catalog screen as a free entry point. *Why it matters:* Top-Lab's existing pattern (M22 Database Maintenance, M17 user-management) gates sensitive windows behind the secondary password. Skipping the gate would be inconsistent with the established product surface and would skip the M17 permission prompt that the user expects to see before any "system" screen opens.

**Items NOT adopted (genuine divergence with OpenCode, with reasons):**
- OpenCode uses a single bulk `Test.Update(...)` signature; this plan uses per-field typed mutators (Rename, SetReportName, etc.). Both are defensible; the per-field approach is preferred here for single-responsibility guards and finer audit granularity. This is treated as an **open decision** (Q2 below).
- OpenCode provides code-level examples (C#, XAML, FluentValidation snippets). This plan remains at the plan level of detail (validation gates, slice-level responsibilities, file paths). Code-level examples are an implementation task, not a planning task. The plan's own "no code" convention is preserved.

**Open design questions surfaced during cross-review (see dedicated section below):**
- Q1 — PatientTitle scope (already an open question in this plan, re-surfaced).
- Q2 — Test field update pattern (per-field mutators vs. single bulk Update). This is the substantive divergence with OpenCode.

## Total Slices: 8

### S1 — Domain Invariants, Per-Field Mutators, Freeze-Contract Value Object
- **Title:** Domain aggregate finalized with typed per-field `Test` mutators, BR-04-aware `ReferenceRange` predicate, and the `ReferenceRangeSnapshot` value object that carries the freeze contract.
- **User-visible behavior / technical capability:** Domain layer exposes one mutator per editable `Test` field; each emits a named `DomainEvent`. `ReferenceRange.Matches(sex, ageUnit, ageValue)` returns `false` when the request's `AgeUnit` does not equal the row's `AgeUnit` (BR-04). `ReferenceRange.Delete()` performs an unconditional hard-delete on the live row only. `ReferenceRange.CaptureSnapshot()` produces an immutable `ReferenceRangeSnapshot` value object carrying the full reference-range fields + a captured-at timestamp. `ReferenceRangeSnapshot` is a value object owned by M-12's Domain; M-04's `Result` aggregate carries a `ReferenceRangeSnapshot?` property (M-04's job to add the column; M-12 does not migrate).
- **Full-stack reasoning:** Domain-only slice; no Application/Infra/Presentation work yet. Each `Test` mutator validates non-null/non-empty/non-negative (where applicable) before mutating, and raises one `TestChangedEvent` carrying the field name and old/new value. `ReferenceRange` carries `Sex?`, `AgeUnit`, `AgeMin`, `AgeMax`, `MinValue`, `MaxValue`, `LowComment?`, `HighComment?`. `ReferenceRangeSnapshot` is a `record`-style value object (immutable). `PatientTitle`, `TestGroup`, `WorkGroupLog`, `WorkGroupLogItem` get basic factory methods and immutability for identity fields. **`WorkGroupLogItem` — pre-check required before changing its constructor visibility:** the public parameterless constructor (for EF Core) stays; the public parameterized constructor must be made private and replaced with a static `Create(WorkGroupLogId, TestId)` factory. Before making the change, search the entire codebase for `new WorkGroupLogItem(` and confirm no existing call site uses the parameterized constructor; if a call site is found, M-12's slice cannot land until that call site is migrated. `TestComment` is NOT touched here except for a courtesy `Update(string commentText)` method (used by M-13 later; not consumed by any M-12 Application command).
- **Ambiguity resolution:** #1 resolved here — `Test.Update` does NOT exist; only the per-field mutators. #2 + #5 partially resolved — `ReferenceRange.Delete` unconditional; the freeze-contract value object exists in Domain but is persisted by M04.
- **Validation Gate:** xUnit test (`TopLab.Domain.UnitTests`) asserts: each `Test` mutator persists, emits exactly one `TestChangedEvent` with the expected field name and old/new values, rejects null/empty/negative/zero inputs where applicable; `ReferenceRange.Matches` returns `false` when `request.AgeUnit != row.AgeUnit` (BR-04); `ReferenceRange.Delete` removes the row; `ReferenceRange.CaptureSnapshot()` produces a value object with byte-equal fields for the source range (immutability); `WorkGroupLogItem.Create(...)` produces a valid item and the previous public parameterized constructor is no longer callable from outside the assembly (verified by a compilation test that the pre-check search returned no external call sites).

### S2 — Application Layer (Commands, Queries)
- **Title:** CQRS handlers for catalog, groups, reference ranges, work groups, and patient titles.
- **User-visible behavior / technical capability:** Handlers expose `SearchTests`, `GetTest`, `CreateTest`, `UpdateTestField*` (one per S1 mutator), `CreateTestGroup`, `UpdateTestGroup`, `CreateReferenceRange`, `UpdateReferenceRange`, `DeleteReferenceRange`, `CreateWorkGroupLog`, `AddWorkGroupLogItem`, `RemoveWorkGroupLogItem`, `CreatePatientTitle`, `UpdatePatientTitle`, `DeactivatePatientTitle`, `GetWorkGroups`, `GetPatientTitles`. `DeleteReferenceRange` removes the live `ReferenceRange` row only — no other rows touched. `UpdateReferenceRange` writes a NEW `ReferenceRange` row (versioning); old rows remain in the table for audit/lookup but are flagged as superseded. **No `ResultReferenceRangeSnapshot` row is written by M-12's Application layer; M-04's Result entry path is responsible for invoking `ReferenceRange.CaptureSnapshot()` and storing the snapshot on the new Result.** **`SearchTests` query includes a numeric-vs-text branch:** the handler attempts `int.TryParse(SearchTerm)` — on success, the search includes `t.Id.Value == parsedInt` joined with OR to the existing text matches on `Name` / `ReportName` / `Barcode`, satisfying FR-M12-001's explicit "test number" search axis.
- **Full-stack reasoning:** Application layer (MediatR-style handlers per M22 pattern). Pipeline `Validation → Authorization → Logging` per M22. FluentValidation in `Application/Validation`. Each handler depends on `IUnitOfWork` (M17) and the repositories declared in S3 (interface-only here, implementations land in S3). `DeleteReferenceRange` returns `Result<Success>`; the snapshot-preservation guarantee is asserted by M-04's own tests (M-12's tests cover the live-row side).
- **Ambiguity resolution:** #2 + #5 finalized for M-12's surface — M-12 owns the live row, M-04 owns the snapshot persistence. #4 enforced — every handler maps to one of the eight slices.
- **Validation Gate:** xUnit Application-handler tests assert: (a) `DeleteReferenceRange` succeeds and removes the live `ReferenceRange` row; (b) `UpdateReferenceRange` produces a new version row with a fresh `ReferenceRangeId` and flags the previous version as superseded; (c) no M-12 command writes to a `ResultReferenceRangeSnapshot` table (verified by a repository test that no such table is registered in `ApplicationDbContext`); (d) `SearchTests` with a numeric `SearchTerm` (e.g., "42") returns the test whose `Id.Value == 42` plus any tests whose `Name`/`ReportName`/`Barcode` contains "42"; with a non-numeric term, the numeric branch is skipped.

## Open Decisions Requiring Owner Approval

These are presented as explicit open questions, not silently resolved. Each one requires the owner's decision before being baked into the implementation.

### Q1 — PatientTitle scope
- **Question:** Should `PatientTitle` (creation / update / deactivation) be included within M-12's scope, or does it belong to a different module (e.g., M02 Patient Registration, M03 Patient Billing)?
- **Recommendation:** Keep it in M-12 (the current plan's choice). Rationale: (a) M-12 is the System-pane configuration surface; titles are used at patient entry (M02) but defined as system data; (b) including it avoids a phantom "where do titles come from" gap for M02; (c) the F5 schema is in place and the only behavior needed is basic CRUD; (d) cost of moving it later is low (one module owns PatientTitle; refactor is mechanical).
- **Trade-off:** if M02 (Patient Registration) is built before M-12 ships, M02 will need to either wait or read titles via a stub. If M-12 is built first (the dependency order), this is a non-issue.
- **Status:** Open. The plan keeps PatientTitle in M-12; the owner may decide otherwise.

### Q2 — Test field update pattern
- **Question:** Should `Test` field edits use separate per-field typed mutators (`Rename`, `SetReportName`, `SetReceiptName`, `SetGroup`, `SetBarcode`, `SetCompletionDuration`, `SetSentOutFlag`, `SetSentOutPrice`, `SetPatientPrice`, `SetLabToLabPrice`) — finer audit granularity, higher implementation cost — or the existing single bulk `Update` method (simpler, coarser audit granularity)?
- **Recommendation (this plan's current choice):** per-field typed mutators.
  - *For:* single-responsibility guards (e.g., `SetCompletionDuration` rejects negative values without burdening the other setters); finer audit trail (one `TestChangedEvent` per field with field name + old/new value); UI staged-edit pattern maps naturally to per-field commands; the existing `Test.Update` is already partial (does not accept all 8 fields) so extending per-field is more orthogonal than fixing the bulk signature.
  - *Against:* 10 method names vs. 1; more handler boilerplate in S3; the existing `Test.Update` becomes dead code (must be removed or marked obsolete).
- **Alternative (OpenCode's choice):** keep / extend the single bulk `Update` method.
  - *For:* one Application command per save action (1 `UpdateTestCommand` instead of N `UpdateTestField*`); simpler handler; less duplication of guard logic; if multiple fields are dirty, fewer transactions.
  - *Against:* coarser audit trail (one event names all changed fields, but loses old/new for each); one method must validate all 8 fields at once; the original PRD wording "fields can be modified" doesn't say "individually."
- **Status:** Open. This plan adopts per-field mutators; the owner may switch to bulk `Update` and the plan will adapt.

## Factual Technical Answer (Q3)

**Q3 — Result entity snapshot behavior:** Does the `Result` entity store its own independent copy of the reference-range values and the pass/fail evaluation at the time a result is entered, or does it rely on a live reference to the `ReferenceRange` table that would change retroactively if that range is later edited?

**Answer (with direct evidence):** No. The current `Result`-equivalent aggregate in the codebase does **not** store any reference-range snapshot. The relevant entities live under `src/TopLab.Domain/Results/`:

- **`src/TopLab.Domain/Results/PatientTest.cs`** (157 lines, the central order/result line — per its own XML doc-comment: "Central order/result line. Auditable; hosts T-audit columns"): the entity exposes `ResultValue` (string), `ResultFlag?` (enum: NORMAL / ABNORMAL / CRITICAL, presumably), `Notes` (string?), `EnteredByUserId`, `EnteredAtUtc`, `IsReviewed`, `ReviewedByUserId`, `ReviewedAtUtc`. It does **not** expose any `ReferenceRangeId`, `MinValue`, `MaxValue`, `LowComment`, `HighComment`, `Sex`, `AgeUnit`, `AgeMin`, or `AgeMax` field.
- **`src/TopLab.Domain/Results/ProfileResultItem.cs`** (64 lines): exposes `AnalyteName`, `ResultValue`, `Unit`, `ProfileResultFlag?`, `IsVerified`, `IsPrinted`. No reference-range fields.
- **`src/TopLab.Domain/Results/CultureResult.cs`** and **`src/TopLab.Domain/Results/CultureAntibioticResult.cs`**: a repository-wide `grep` for `ReferenceRange|MinValue|MaxValue|LowComment|HighComment|Sex\b|AgeUnit|AgeMin|AgeMax|Snapshot` against `src/TopLab.Domain/Results/CultureResult.cs` and `.../CultureAntibioticResult.cs` returned **zero matches**.
- A repository-wide search for any class with a name containing "Snapshot" or "ResultReference" or "Frozen" across `src/TopLab.Domain/` returned **zero matches**.

**Consequence for this plan:** today, the `PatientTest.ResultValue + ResultFlag` row alone does not carry a frozen reference range. The pass/fail evaluation against a `ReferenceRange` is presumably resolved at query/read time (M04 territory). The freeze contract this plan assumes — `ReferenceRangeSnapshot` value object captured on `Result` rows — **does not exist in the codebase today**; it is the new Domain shape M-12 introduces in S1, and the actual snapshot column on `Result` is M-04's job (per ambiguity #5).
